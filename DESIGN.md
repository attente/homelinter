# homelinter Design Specification

## Overview

homelinter organizes home directories: it scans files, analyzes them, generates reorganization suggestions, and executes those suggestions automatically or interactively.

One service owns scanning, analysis, planning, validation, and execution. The CLI, TUI, and SPA are clients of that service. The CLI and TUI launch an invocation-scoped service, while `homelinter web` launches a service that remains available until terminated.

**Non-goals**: homelinter is not transactional across operations, does not emulate host capabilities that are unavailable, and does not guess at semantics it cannot verify safely (see "Execution & Safety").

## Platform Scope

homelinter supports Linux, macOS, and Windows as first-class platforms. The native executor and filesystem safety checks are the reference implementation on every platform. Platform-specific behavior is selected at runtime and is never inferred from Unix command syntax alone.

Linux and macOS may export POSIX shell scripts. Windows supports drive-letter and UNC paths and exports PowerShell scripts. Exported scripts are platform-specific, are not portable between operating systems, and are always produced for the host platform.

Paths, path comparison, filename validation, file identity, timestamps, permissions, links, and metadata preservation use host-platform semantics. Serialized plans and audit records retain host-native absolute paths and include the platform identifier. A capability unavailable on the host is reported as unsupported or failed rather than emulated unsafely.

On Windows, homelinter classifies symbolic links separately from every other reparse point, including junctions, mount points, and filesystem-specific tags. Only symbolic links are indexed or repaired; all other reparse points are never followed, traversed, indexed, or modified. Windows link operations require the permissions and operating-system features needed by the selected link type.

## Core Principles

- **Safety first**: homelinter never overwrites an existing object, modifies file contents, follows an unsupported link, or executes a stale or colliding operation.
- **Non-destructive by default**: scanning, analysis, and planning never modify the filesystem. A plan export writes a script file to the user-specified path but never modifies the scanned home tree; destructive operations on the scanned tree require explicit execution authorization.
- **Honest failure reporting**: operations are validated immediately before execution, and failures and partial completion are reported precisely without claiming rollback that did not occur.
- **Leverage existing tools**: prefer modern Rust tools (`fd`, etc.) over older counterparts (`find`), with graceful fallbacks.
- **Convention without explicit configuration**: infer sensible defaults from the user's existing directory structure, patterns, and installed tools in the absence of explicit configuration.
- **User in control**: all preferences are overridable via command-line arguments and configuration files.

## Scan Root and Path Representation

The user may instruct homelinter to scan any accessible directory with the CLI `--root <path>` option or the corresponding `scan.root` setting in an interactive client. The scan root is a persistent runtime setting: `--root` at launch seeds the initial effective settings, and an interactive client edits `scan.root` through the settings API, which writes the configuration file. If no scan root is set, the scan root is `$HOME`.

The scan root defines the root of the primary discovery tree: homelinter discovers and analyzes files, directories, and repository units only at or below that root, subject to the hidden-file, ignore, and exclusion rules. It does not limit where a discovered object may be moved.

All filesystem paths in suggestions, exported plans, client APIs, and user-facing output are absolute paths in the host platform's native representation. This includes the scan root, `target`, and `new_path`. Paths are never interpreted relative to the process's current working directory, the scan root, or the platform's home directory. A destination may be outside the scan tree and outside the user's home directory, for example on a mounted USB device. Destination selection remains subject to configured permissions and execution safety checks.

- Input paths for `--root`, configuration, and target directories are resolved according to their documented input rules and converted to absolute paths before scanning or planning.
- Emitted paths must be normalized absolute paths using host-platform rules. They must not contain `~`, environment-variable references, redundant `.` components, or a relative-path prefix.
- Unix paths, Windows drive-letter paths, and Windows UNC paths are accepted according to the host platform; paths are not converted between platform syntaxes.
- Normalization must not resolve symlinks merely for display or serialization. The lexical absolute path and the filesystem identity it names must be preserved separately where necessary.
- The scan root is captured when the scan starts and is retained with the scan and execution plan. A later change to the process's current working directory or environment must not change the meaning of a suggestion.
- Before execution, `target` must still identify the discovered source object, and a `move` destination may be anywhere allowed by the plan. The destination is not required to be under the scan root or `$HOME`.

`target` and `new_path` in a Suggestion are absolute paths. Internal APIs use platform-native path types, while client and serialization boundaries emit absolute paths in the host platform's representation. Audit records use the same representation and record the host platform.

## Symlink Handling

Symlinks are not ordinary discovery units and receive a separate treatment from primary discovery.

**The home-wide symlink pass** is the deliberate exception to the scan-root boundary. For every scan, homelinter also performs a separate symlink pass over the entire user's home directory, regardless of `scan.root`. This pass finds symlinks that need repair when a discovered source is moved or deleted. It records symlink entries and their raw targets but does not follow symlinks or scan their target contents. The pass includes symlinks in hidden and VCS-ignored directories; `scan.root` does not restrict it, and `scan.exclude_paths` does not exclude symlinks from it, because doing so could leave references to moved or deleted objects broken.

The pass derives its scope from the platform's home environment variable resolved at scan start; the resolved home path is captured with the scan, so a later environment change does not change the repair-pass coverage. The pass collects only the metadata needed for repair - absolute link path, raw link target, link type, and the resolved target identity when resolvable - and never reads symlink target contents. This is a deliberate scope and privacy trade-off: a scan rooted below `$HOME` still reads symlink metadata across the entire home directory (including hidden and VCS-ignored directories) to keep moves and deletes from breaking links. Repairs are never performed for links unrelated to a planned move or delete, so a narrow scan gains no repairs outside its own suggestions.

**Primary scan**: the primary scan never follows symlinks. Directory symlinks are recorded but never traversed or analyzed as directories. The pass preserves each link's raw target and whether that target is relative or absolute, because repair must preserve the link's intended target while accounting for the link's parent directory.

**Repair**: during execution, symlinks in the home-directory index are eligible for repair only when their target is the source of a planned `move` or `delete`. A link to a moved file or directory is repaired to point to the new absolute target, represented in the link using the appropriate relative or absolute form. A link to a deleted duplicate is repaired to point to the retained original only when the duplicate relationship and target identity were confirmed.

Repair is always performed under safe-only semantics: only links whose recorded identity and target were confirmed at scan time are repaired, unsupported reparse points are never followed or modified, and a repair is validated again immediately before it runs. Repair applies only to the link's path target metadata and never changes file contents. It preserves whether the original link target was relative or absolute: relative replacement targets are recalculated relative to the symlink's parent directory, while absolute replacement targets remain absolute.

- For a moved directory, symlinks targeting the directory or any descendant are associated with the move and are repaired using the corresponding old-to-new path mapping.
- For a deleted duplicate, symlinks to the deleted object may be repaired to point to the retained original only after the delete operation's preconditions and duplicate identity are confirmed.
- Immediately before the parent operation, homelinter validates the symlink path, raw link target, and resolved target identity against the scan-time record. Immediately before repair it re-validates that the path is still a symbolic link and still carries the recorded raw target; the resolved identity is not re-resolved at that point, because the parent operation usually moved or deleted the object it resolved to, and the parent's own preflight already confirmed that object. The repair replaces the link without following it, staging a new link beside it and renaming it over the old one on Unix, so an interruption leaves either the old or the new link and never no link at all (Windows removes then recreates, a documented seam).

Repair is a dependent `repair_symlink` operation (see "Suggestion Model"); it exists only as a dependency and is never surfaced or executed independently.

## File Classification

homelinter categorizes files into **Asset Kinds**:

| Kind | Description | Example Extensions |
|------|-------------|-------------------|
| `document` | Text documents and office files | `pdf`, `docx`, `odt`, `txt`, `md`, `epub` |
| `photo` | Raster and vector images | `jpg`, `jpeg`, `png`, `gif`, `webp`, `svg`, `raw`, `cr2`, `nef` |
| `video` | Video files | `mp4`, `mkv`, `avi`, `mov`, `webm` |
| `audio` | Music and sound files | `mp3`, `flac`, `ogg`, `m4a`, `wav`, `aac` |
| `repository` | Version control repositories | `.git`, `.hg`, `.svn` (detected by a directory marker, or a `.git` file) |
| `archive` | Compressed files and installer packages | `zip`, `tar`, `gz`, `bz2`, `7z`, `rar`, `dmg`, `deb`, `rpm`, `apk`, `msi`, `exe`, `bin` |

**Unmanaged files**: homelinter only operates on files it can name from
content metadata or relocate safely as an atomic unit. Every other file is
unmanaged: it is never extracted, hashed, moved, or deduplicated, and no
suggestion is ever generated for it. Structured data and configuration
files (`json`, `toml`, `yaml`, `csv`, `sql`, `db`, `sqlite`, `ini`, `conf`,
lockfiles, and similar), source and script files (`py`, `rs`, `go`, `c`,
`h`, `cpp`, `js`, `sh`, and similar), and any unknown or extension-free
name classify to no kind because they live where their software expects
them: relocating or deduplicating them would break the reader, so the tool
leaves them strictly alone. There are no `data`, `executable`, or `other`
kinds.

**Empty files**: files of zero bytes are completely ignored. They are not scanned, not classified, and no suggestions are generated for them. They are never duplicates regardless of hash.

**Hidden files**: whether hidden files and directories are scanned is the persistent `scan.hidden` setting, resolved exactly like the scan root. The CLI selects it with `--hidden`, and the TUI and SPA edit `scan.hidden` through the settings API. By default, when no setting is given, hidden files and directories are excluded. When using `fd`, homelinter passes explicit flags (regardless of `fd`'s own defaults) to enforce this convention, consistent with `scan.exclude_paths` and the selected hidden setting. `find` is invoked with arguments that match the intended scope. The operation is deterministic from homelinter's configuration; tool defaults do not influence behavior.

**Hidden-file definition by platform**: what counts as hidden is platform-native. On Linux and macOS, a path component at any depth (excluding `.` and `..`) is hidden when its name begins with a dot; VCS ignore rules are never consulted, because repositories are atomic units whose contents are never descended into, and dotfile classification does not read ignore files. On Windows, the definition is configurable via `scan.hidden_definition` (see "Configuration File Schema"): `explorer` (default) - an object is hidden when it has the Hidden or System file attribute, the union Explorer and common search tools treat as not displayed by default; `attribute` - the Hidden attribute alone; `dotfiles` - names beginning with a dot, matching Unix semantics. The definition gates only primary discovery, just like the boolean `--hidden` itself, and never the home-wide symlink repair pass; it is applied deterministically from the configuration value, never from the shell's or Explorer's display settings.

**Repositories**: a directory is classified as `repository` if it contains a `.git` directory or `.git` file, a `.hg` directory, or a `.svn` directory. The `.git` file form covers git worktrees and other detached marker setups, whose marker is a regular file (a `gitdir:` pointer) rather than a directory. A repository is treated as an atomic unit: its contents are not scanned, classified, hashed, or analyzed, and the tool may suggest moving or renaming only the repository root, never restructuring internals. VCS ignore rules do not control repository discovery or primary discovery; repositories are detected structurally. Nested repositories (including submodules) are ignored for scanning and classification, but they remain physically inside the parent repository and move with it if the parent root is relocated.

**Symlinks**: see "Symlink Handling".

## Analysis Pipeline

For each discovered file or repository unit in the primary scan, homelinter collects:

1. **Filesystem metadata**: size, modification time, creation time, permissions, owner
2. **Kind-specific metadata**:
   - Photos/Videos: EXIF / IPTC / XMP data (date taken, camera, GPS, orientation)
   - GPS coordinates from photos and videos are reverse-geocoded to a locality by the configured geocoder when it is enabled, reduced to the city (or a finer neighbourhood for configured cities; see "Destination Path Format Strings")
   - Documents: title, author, and creation date from embedded container metadata; page count is available for PDFs only (see "Tooling Strategy")
   - Audio: ID3 tags, bitrate, duration
   - Repositories: remote URLs, default branch, commit count, last activity, collected by the per-VCS adapter (see "Tooling Strategy")

Provider-derived location (`%l`) and description (`%s`) values are resolved **asynchronously, after the scan**: the scan plans and enqueues provider requests before publishing, marks the suggestions that depend on them `metadata_pending`, publishes a `suggestion.batch` event carrying the batch total immediately (clients fetch the rows themselves through the paged `GET /suggestions`; see "Events (SSE)"), and a background worker fetches the queue with per-provider rate limits (see "Provider Plugins > Offline request loop"). **A provider is consulted only when the destination format for a unit's kind actually uses the corresponding placeholder**: a geocode request is planned only for a unit whose format contains `%l` and that carries raw GPS coordinates, and a description request only for a unit whose format contains `%s` (or, for a document, `%t`), with a description provider enabled for its kind and no authoritative title already available in embedded metadata, and a document-author request only for a document whose format contains `%a` and whose embedded metadata carries no author; format strings without the placeholder never trigger a provider call for that unit. Redundant duplicates are never planned for provider work: a redundant copy receives exactly one delete suggestion and never a move, so provider metadata cannot reach a rendered destination for it, and because a move and a delete for the same path share the stable `id_for_target`, keeping the unit out of the provider queue also prevents a background rebuild from overwriting the delete with a move. A pending suggestion is visible as a `scanning <filename>` row with a small animated spinner in the TUI and web UI, but **not executable** until every provider request for its unit resolves, so a user can never execute a move built on incomplete metadata. When the last request of a unit resolves, the suggestion is updated in place by its stable id: a success rebuilds the move with the collected values, a failure keeps generated fallbacks, using an existing embedded title or the original filename stem without its extension for `%s` (and the next scan retries), and `metadata_pending` flips to `false`. The batch is then re-validated against the now-real metadata: a destination that only collides once the provider value is applied is rejected with a reason (broadcast as `batch.validated`), while a pending suggestion that would have lost a provisional collision stays pending. Clients receive a `suggestion.updated` event for the one row that changed (or `suggestion.removed` when a rebuilt move now says the file stays put), so a large batch is never re-cloned or re-broadcast on each resolution, alongside a `metadata.progress` event reporting how many of the suggestions that originally had provider requests have had all of theirs resolve. A scan is never blocked on a provider request, and a new scan supersedes outstanding requests from the previous one via a per-session epoch. A single move suggestion's provider metadata can also be re-requested on demand, discarding its cache entries and re-planning its jobs from the current configuration without a new scan (see "Provider Plugins > Offline request loop").
3. **Content-derived metadata** *(optional, user-configurable)*:
   - An LLM analyzes document subject matter (e.g., "invoice", "travel photo", "tax document")
   - A description service produces a short description of the content, used by the `%s` placeholder; for a document whose format uses `%t` but not `%s`, the same request also supplies the title. Descriptions are LLM-backed today through the provider settings in `[description]`; photo descriptions may also send raster image bytes to an image-capable backend (`ollama` with a vision model) so the model analyzes pixels rather than guessing from the filename - photos larger than `max_image_dimension` are downscaled before the request, SVGs are rasterized in-process with `resvg` and send extracted text alongside the pixels, and video descriptions send representative frames (about one per second, capped by `max_video_frames`) through the same vision backend, while audio recognition remains future work behind a separate provider interface. A configurable default provider (the base `[description]` entry) may serve the content-modality kinds, with per-modality providers overriding it when needed; kinds without a content source never get a description provider, so `%s` uses an existing embedded title or falls back to the filename stem for them. The built-in wording for text documents asks the model to recover the document's full original title first and to return keywords only when no title is stated; the base entry and the other modalities keep the keyword wording. A unit whose embedded metadata already carries an authoritative title (document/container title, ID3 title, EXIF title) never receives a description provider request at all: the title is used verbatim as `%s`, so a titled file incurs no LLM cost.
   - Documents are preprocessed to plain text before the description service runs, using the configured extraction tool for their format (see "Tooling Strategy"). Text extraction is disabled by default and incurs no cost when the description service is off.
   - The model and provider backend are configurable by the user (local via Ollama/LM Studio, or remote via OpenRouter; see "Provider Plugins")
   - LLM analysis and description services are **disabled by default** and incur explicit cost/privacy trade-offs
   - Reverse-geocoding and description results are stored in a persistent cache so repeated scans do not make redundant requests and continue to produce stable user-readable values.
4. **Filename- and path-derived metadata**: the filename and relevant parent-directory path may be analyzed by an optional LLM when higher-priority metadata and content-based analysis do not provide the requested value. This analysis reads only the name and path, never the file bytes. It is distinct from the `%f`, `%F`, `%n`, and `%e` placeholders, which use the filename directly. Filename-based LLM analysis is **disabled by default**, uses the same configurable-provider and persistent-cache machinery as content-derived metadata, and is the last metadata-analysis stage before placeholder-specific generic fallbacks.

For format-string metadata, the general precedence is: kind-specific embedded document or media metadata first, then content-based analysis (including document preprocessing such as `pdftotext` before an LLM request), then filename/path analysis by LLM, and finally the placeholder's generic fallback. A placeholder may omit sources that cannot produce that kind of value, but a lower-priority source must not override a value from a higher-priority source.

## Suggestion Model

A **Suggestion** is a proposed change to the filesystem. There are two user-facing suggestion types:

| Type | Description | Example |
|------|-------------|---------|
| `move` | Relocate and/or rename a file or directory | `/home/alice/Downloads/photo.jpg` -> `/home/alice/Pictures/2024/photo.jpg` |
| `delete` | Remove a redundant file | `/home/alice/Desktop/copy.pdf` (duplicate of `/home/alice/docs/original.pdf`) |

Move destinations are produced by the destination format string for the target's Asset Kind (see "Destination Path Format Strings"). The format string resolves to the complete new path relative to the platform's home directory (or an absolute path). A filename placeholder controls whether the moved object keeps its original name or is renamed.

**Suggestion properties**:
- `target`: Absolute path to a file or directory
- `type`: `move` or `delete`
- `new_path`: Proposed absolute destination (for `move` only)
- `reason`: Human-readable explanation. It is empty for `move` suggestions: the source and destination paths already state the operation, so moves carry no separate prose (the preview panes render only the `from`/`to` paths). Delete suggestions carry the duplicate/keeper explanation.
- `metadata`: Structured data supporting the suggestion (e.g., "extracted date: 2024-03-15"). Move suggestions carry file and EXIF facts when the extractors found them: `date_source` (always present: `embedded`, `filename`, or `filesystem` for the modification-time fallback), `extracted_date` (date and time, when a date was extracted), `date_offset` (the capture UTC offset when the file records one, e.g. `+09:00`), `size`, `bitrate_kbps`, `duration_secs`, `page_count`, `camera`, `title`, `author`, plus GPS coordinates (`latitude`, `longitude`) and the reverse-geocoded `location` name when one resolved. Delete suggestions carry `duplicate_of` (the retained keeper) and `size`.
- `dependent_operations`: Filesystem operations that are required because this suggestion is executed; these operations are not independently selectable

**One suggestion per target**: homelinter produces exactly one top-level suggestion per file or repository unit. (If no reorganization is warranted, no suggestion is generated.) Moves apply only to files and repository roots. Ordinary directories are discovered and analyzed for structure inference, but they are not themselves targets of reorganization or deletion suggestions. Internal analysis may evaluate multiple candidates, but only the single best primary operation is surfaced. Dependent symlink repairs belong to their parent suggestion and do not violate this rule. Suggestions never modify file contents.

**Dependent operations**: a move suggestion may have zero or more dependent `repair_symlink` operations, and a delete suggestion may have repairs attached when deleting the target would otherwise leave a confirmed symlink broken. Each dependent operation identifies an absolute symlink path, the symlink target recorded during analysis, and the replacement target to write after the parent operation. The primary operation is the dependency's cause. The parent and all of its dependent repairs form one execution unit: dependent operations are mandatory members of the execution plan, are executed only if the parent operation succeeds, are not independently selectable, rejectable, or executable, and never run if the parent is rejected, deselected, or otherwise excluded from the execution batch. A symlink repair is never surfaced or executed as an independent suggestion. Dependent operations do not change file contents of either the moved/deleted object or the symlink target.

Interactive clients may select top-level suggestions; dependent operations always follow their parent. CLI execution and export operate on the complete generated batch.

### Deduplication Semantics

- **Content verification**: SHA-256 is the only hash algorithm used. The full-content SHA-256 hash is the only hash that determines membership in a duplicate group. For files larger than the configured threshold, a fast-path SHA-256 hash is computed from the first 1MB concatenated with the last 1MB and the total file size encoded as an 8-byte little-endian unsigned integer (in that order, with no separator). The fast path is a shortlist only: files whose fast-path hash already matches are queued for a full-content hash, and only files whose verified full-content hashes match are grouped and considered for `delete` suggestions. The fast path never establishes a duplicate relationship or a delete suggestion by itself. A full-content hash is computed on demand whenever a group's membership must be confirmed. The fast-path hash is also retained as the content fingerprint that keys a file's provider description and author cache entries when no full hash was computed for deduplication, so those caches stay content-keyed without forcing a full read of large media (see "Cache Implementation").
- **Duplicate groups**: a duplicate group is the set of files whose verified full-content hashes match. Only managed files participate: unmanaged files are filtered out at analysis time and are never hashed, so they can never form or join a group. Each group is reported as a finding during analysis. For every redundant file in a group (all except the preferred keeper), homelinter suggests `delete`, and the preferred keeper may be moved to a new suggested path and name when its inferred destination differs from its current path. The keeper is a move candidate under exactly the same resolution, validation, and safety rules as any non-duplicate file: it receives a `move` suggestion if and only if the resolved `new_path` differs from its current absolute path (per "Destination Path Format Strings"), the move passes destination resolution and batch validation, and no metadata-preservation suppression applies to the group. A keeper whose move is suppressed or rejected receives no suggestion and keeps its current location, exactly like any other file whose move fails validation; a blocked sibling delete never blocks or changes the keeper's move. A redundant copy never receives a move or any other suggestion: its one top-level suggestion is the `delete`, so "one suggestion per target" holds even when the same copy would otherwise be a move candidate. Delete suggestions are always file-level: deduplication operates on file content hashes, and a repository root is an atomic unit that is never a deletion candidate.
- **Conflict resolution**: when duplicates are confirmed, the oldest file (by creation time; fallback to modification time) is preferred. Newer copies receive exactly one suggestion each.
- **Metadata preservation**: if the newer duplicate has better metadata (e.g., more complete EXIF), homelinter emits a warning and suppresses the executable suggestion for the conflicting files. The warning is carried in the scan result's warnings and therefore the session's `warnings`, so clients can surface it; the files are left untouched until manually reviewed. `GET /session` exposes the list, and the CLI, TUI, and SPA surface it (the SPA as a banner above the suggestion list).

## Directory Structure Inference

In the absence of explicit configuration, homelinter infers the user's preferred organization by scanning existing top-level directories in `$HOME`:

1. Detect standard directories (`Documents`, `Downloads`, `Pictures`, `Music`, `Videos`, `Desktop`, `.config`, etc.)
2. Identify user-created organizational patterns (year-based folders, project folders, client folders)
3. Map Asset Kinds to inferred destinations using folder names and existing file distributions
4. Infer destination format strings from recurring structural patterns: a `Pictures/2024/03` layout suggests `Pictures/%Y/%m/%f`, a flat `Music/<artist>` layout suggests `Music/%a/%f`, and a flat directory with no recurring structure infers `Projects/%f` or another `%f`-suffixed directory for the matched kind
5. Confidence weighted by: number of existing files, consistency of pattern, recency of use

With **explicit configuration**, `target_paths` directly maps Asset Kinds to destination format strings and overrides inferred defaults. Platform user-directory APIs contribute only to inferred defaults (precedence level 3) and never override explicit `target_paths`; `xdg-user-dir` is used on Linux where available, with platform-appropriate equivalents on macOS and Windows.

## Destination Path Format Strings

A destination format string is a printf-style template that determines the new path of a discovered object, relative to `$HOME` or absolute. Every Asset Kind has exactly one destination format string at any point, resolved by the standard precedence (see "Configuration"). A format string resolves to the complete new path of the moved object; the final `new_path` of a move suggestion is the resolved path.

### Syntax

- The resolved string is interpreted relative to the platform's home directory unless it uses the host platform's absolute-path syntax, in which case it may point anywhere allowed by the operating system, including outside the home directory and on another filesystem.
- `%%` emits a literal percent sign.
- Every other `%` must be followed by a supported placeholder character. An unknown placeholder is an error at configuration and parse time: it is rejected rather than emitted literally, so typos fail fast instead of producing surprising paths.
- Placeholders may repeat and may be combined in any order, for example `Pictures/%Y/%m/%f` or `Music/%a/%Y/%t.%e`.
- A format string must contain at least one placeholder and must name the target file. A format string with no placeholder names a fixed file and is an error at configuration and parse time. A format string that resolves to an empty path, or whose final segment is empty, is also rejected: it must not end with a path separator or an empty value. The original filename is never appended implicitly, and a trailing `/` is not special.
- The original filename is optional. Omitting the filename placeholders (`%f`, `%F`, `%n`, `%e`) discards the original name and names the target from metadata alone, for example `Pictures/%Y/%m/%s` or `Pictures/%s_%Y%m%d`. Date and metadata placeholders always produce a non-empty value, so such a format still yields a valid filename.

### Placeholders

| Placeholder | Meaning | Primary source | Fallback |
|---|---|---|---|
| `%Y` | four-digit year | extracted date (EXIF date taken, ID3 date, document date) | modification time |
| `%y` | two-digit year | extracted date | modification time |
| `%m` | two-digit month (`01`-`12`) | extracted date | modification time |
| `%d` | two-digit day (`01`-`31`) | extracted date | modification time |
| `%H` | two-digit hour (`00`-`23`) | extracted date | modification time |
| `%M` | two-digit minute (`00`-`59`) | extracted date | modification time |
| `%S` | two-digit second (`00`-`59`) | extracted date | modification time |
| `%t` | title | manual override, then document title, ID3 title, EXIF title, repository name | content-derived title or description (the description provider recovers a document's original title, falling back to keywords), then filename/path analysis by LLM, then filename stem |
| `%a` | author / artist | manual override, then document author, ID3 artist, EXIF artist, or for a document with no embedded author the text description provider's inference | omitted when no source produces a value |
| `%l` | location | manual override, then GPS metadata reverse-geocoded to a place name, reduced to the city (or a finer neighbourhood for configured cities) | omitted when no place or coordinates are available |
| `%s` | subject / description | manual override, then an existing embedded title (document/container title, ID3 title, EXIF title) when present, else the selected content-modality provider (per-modality override for the kind, else base); kinds without a content source have no provider | filename stem |
| `%c` | camera model | EXIF camera model | omitted when metadata is absent |
| `%h` | remote host | repository remote URL host (e.g. `github.com`) | empty (segment omitted) |
| `%o` | remote owner | repository remote URL owner/username, the first path segment after the host (e.g. `github.com/<owner>/<repo>`) | empty (segment omitted) |
| `%k` | asset kind | classification | always available |
| `%f` | original filename, including extension | original filename | always available |
| `%F` | original filename, lowercased with whitespace and separator punctuation replaced by hyphens | original filename | always available |
| `%n` | filename stem (original filename without its extension) | original filename | always available |
| `%e` | extension lowercased, without the leading dot; empty when the file has no extension | original extension | always available |

**Fallbacks**: format-string metadata follows the general order: kind-specific embedded metadata, content-based analysis, filename/path analysis by LLM, and then the placeholder-specific generic fallback. Date placeholders use an extracted date from that hierarchy and fall back to the file's modification time, which is always available. Date extraction may also inspect the filename as an implementation detail when higher-priority metadata does not provide a date. Recognized filename forms are implementation-defined and may include examples such as `IMG_20240315_153045.jpg`, `PXL_20240315_153045123.jpg`, `2024-03-15.jpg`, and `20240315.jpg`; this list is illustrative, not exhaustive. Filename-derived dates must be parsed conservatively and must not override a date from a higher-priority source. `%t` uses document or media title metadata first, then content-derived subject matter or description (for a document, the description provider is asked to recover the original title first and to return keywords only when the document states none), then filename/path analysis by LLM, and finally the filename stem. A content-derived value or filename stem used for `%t` or `%s` has a duplicated trailing known document extension removed (the stem of `Name.docx.pdf` is `Name.docx`), so the real extension supplied by `%e` is not doubled; an authoritative embedded title is never altered. `%s` uses a saved manual override, then an existing embedded title (document/container title, ID3 title, EXIF title) before the content-description provider, then filename/path analysis by LLM and the filename stem (the original name without its extension) when no description is available, whether no provider was applicable or a provider failed. When a title already exists the description provider is not invoked at all, so a titled file incurs no provider call and keeps the authoritative title; the title is used verbatim as `%s` (subject to the normal sanitization). `%l` uses a saved manual override first, then reverse-geocoded location when available, and falls back to embedded GPS as comma-separated decimal degrees with six fractional digits when coordinates exist but reverse geocoding is unavailable or fails. `%a` uses a saved manual override first, then embedded artist/author metadata (EXIF, ID3, PDF, or office-document/container), and for a document with no embedded author falls back to the text description provider's inference; when none of those produce a value, `%a` is omitted from the filename. The remaining camera placeholder (`%c`) is likewise omitted when metadata is absent or extraction failed. An answer that normalizes to the literal `unknown` counts as no answer.

**Date and time zone semantics**: date placeholders render a zone-less wall clock and homelinter never converts it. An embedded photo or video date (EXIF `DateTimeOriginal`, or the ID3/container equivalent) is used exactly as the recording device wrote it, so a photo taken in Tokyo renders Tokyo local time even when the scan runs in another zone. When the file records a UTC offset (`OffsetTimeOriginal`, falling back to `OffsetTimeDigitized`/`OffsetTime`, or to the offset embedded in a `CreationDate` fallback when that fallback supplies the date), that offset is carried through as `date_offset` metadata for inspection and ordering, but it does not alter the rendered filename. A date parsed from the filename is likewise taken as written. Only when neither an embedded nor a filename date exists does the placeholder fall back to the file's modification time, which is an absolute instant rendered in the scanning machine's local zone; `date_source` reports which of the three applied (`embedded`, `filename`, or `filesystem`). This keeps each kind internally consistent - photo and video names use capture-local time, archive/document/audio names use machine-local time - and means a filename is never silently shifted across zones. Deduplication is unaffected: keeper selection compares the filesystem `created`/`modified` instants (absolute and zone-independent), never the embedded wall clock.

Filename placeholders derive from the original filename, so a format string can rename a file while preserving or dropping its extension, for example `%t.%e` or `%n_%Y%m%d.%e`: `%f` keeps the original case and spacing, `%e` keeps the extension's spacing but lowercases it (so `IMG_0001.JPG` yields `jpg`), while `%F` normalizes the same filename value to lowercase with whitespace replaced by hyphens.

### Resolution & Sanitization

- The format string is resolved per target at suggestion-generation time using the metadata collected during analysis; the resolved path is captured in `new_path`, and later metadata changes do not alter an already-generated suggestion. A resolved path equal to the target's current absolute path (same parent and filename) produces no move.
- The parent directory of the resolved path is created before a move; exported scripts emit `mkdir -p` for it. Clobber prevention, cross-filesystem handling, and deduplication apply identically to resolved and static destinations.
- The same format string applies to files and repository units alike; a repository move uses the `repository` kind's format. A rename produced by a filename placeholder is a `move` like any other, subject to the same validation, safety, and audit rules.
- Suggestions are batch-validated after generation, before display, export, or execution (see "Execution & Safety" - Suggestion Batch Validation).
- The format string is user configuration and is validated rather than sanitized: it must resolve to a non-empty path whose final segment is a filename, and interpolated segments cannot change the path structure.
- Interpolated values are never trusted as raw path text. Each metadata value (`%t`, `%a`, `%l`, `%s`, `%c`, `%F`) is decomposed with Unicode NFD and its combining diacritical marks dropped so accented characters fall back to their basic ASCII equivalent, then lowercased (Unicode-aware), and every run of whitespace or separator punctuation (ASCII punctuation other than `_` and `.`, plus the Unicode dash characters such as the en and em dash) is replaced with a single hyphen, so runs of spaces, hyphens, and other separator punctuation collapse into one; date placeholders contain only digits, `%k` is its canonical lowercase Asset Kind name, and literal text including `%%` is unchanged. A normalized segment therefore can never introduce a path separator or traversal, regardless of source metadata.
  - Path separators (`/`, `\`), NUL, control characters, and platform-invalid characters are replaced with `_`.
  - Leading and trailing whitespace, hyphens, and dots are trimmed after normalization.
  - A value that is empty, or normalizes to `.` or `..`, renders as nothing: the placeholder is omitted from the resolved path together with its adjacent join separators (`-`, `_`, or whitespace), so a missing field never leaves a leading, trailing, or doubled separator. A separator is kept only when it joined two present fields, and a verbatim value such as `%n` is never trimmed. The literal answer `unknown` is treated as no answer and omitted the same way.
  - Provider responses (`%s`, `%t`, `%a`, `%l`) are first normalized to printable ASCII (see "Provider Output Normalization") before this sanitization, so typographic punctuation from a model or geocoder cannot survive as an unusual character in a destination segment.
  - Example: `San Francisco` -> `san-francisco`; `Sunset over the River` -> `sunset-over-the-river`; `Legal Consultation, Employee Intake` -> `legal-consultation-employee-intake`; `William Hua - Offboarding` -> `william-hua-offboarding`; `naïve Café` -> `naive-cafe`.
- Filename placeholders (`%f`, `%n`, `%e`) are the only exception, preserved verbatim with spacing intact; `%e` is lowercased (a case-only transform that cannot introduce an unsafe character) and `%F` is normalized like a metadata value above and is not exempt. This is safe because an existing host filename cannot contain a path separator, NUL, control character, or resolve to `.`/`..`, so it is always a valid destination segment on the same filesystem. Host limits still apply: a resolved destination whose final segment is unsafe - empty, `.`/`..`, containing a path separator, NUL, or control character, or (on Windows) colliding with a reserved device name (`CON`, `PRN`, `NUL`, etc.) - is rejected by batch validation with an `invalid_destination_segment` reason before any operation. The platform's own path-length limit is not pre-checked; an overlong destination fails at execution like any other operation failure. When `%e` is empty, an immediately preceding `.` is omitted, so `%n.%e` degrades to the bare stem.
- `%l` location: resolved by the configured geocoder to a city name (or a finer neighbourhood for cities listed in `geocoder.neighbourhood_cities`; see below), normalized to printable ASCII (see "Provider Output Normalization"), or to the embedded GPS coordinates as comma-separated decimal degrees when the geocoder is disabled or fails; when neither a geocoded place nor coordinates are available the `%l` segment is omitted.
- `%s` subject: resolved using the general metadata precedence: a saved manual override first, then an existing embedded title (document/container title, ID3 title, EXIF title), then the selected content-description provider (per-modality first, then base), then optional filename/path analysis by LLM. A field that carries a manual override is never planned for a provider call for that field, so a user edit can never be clobbered by a background provider result. A unit whose embedded metadata already supplies an authoritative title is never planned for a description provider call, so the title is used verbatim instead of paying for an LLM guess; the description provider is planned only when no title exists. The filename stem (the original name without its extension) is used when no applicable source is available or a provider fails. Kinds without a content source (`repository` and `archive`) never receive a content-description provider - the base `[description]` entry is the default for the content-modality kinds only - so `%s` falls back to an existing embedded title or the filename stem for them; filename-based description remains future work and is not performed today. For documents, the file is first preprocessed to plain text with the configured extraction tool before a content-description request; if no extraction tool is available, the description service receives no text and `%s` falls back to the filename stem. The built-in default prompt for the text modality (documents) asks the model to reply with the document's full original title, preserving the wording, and to fall back to a keyword description only when the document states no title; the generic keyword wording remains the default for the other modalities. The recovered value is used as `%s` and also backs `%t` when no embedded title exists, so a document whose format uses `%t` (but not `%s`) is still planned for the provider. A user-configured `prompt` (base or per-modality) replaces the built-in wording entirely. The request wording comes from the provider's `prompt` template (the built-in wording is the default; see the `[description]` schema), and the full source path and any extracted text are always included (path always, text whenever an extractor produced it), so the model sees the file identity and the document content directly and a custom template cannot omit either. When extracted text exists it is labeled as untrusted data and delimited in a `<document>` block placed first, followed by the `Path:` block and the rendered question last inside a `<question>` block: local models otherwise treat a trailing document as the user's turn and answer the document instead of the question. A request without text (photos and other media) keeps the question first with the path after it. The built-in prompt wording tells the model not to repeat the file type, medium, path, or folder names, and to respect the requested word budget. The completion is used as `%s` after removing any inline chain-of-thought block, trimming surrounding whitespace, and normalizing to printable ASCII (see "Provider Output Normalization"); the built-in framing also instructs the model to answer in printable ASCII; an answer that is exactly `unknown` (case-insensitive) is treated as no answer, so `%s` and `%t` fall back to the filename stem; a completion longer than 24 words or 240 characters is rejected as a provider failure (a second line of defense behind the prompt placement, so a model that answers the document instead of the question cannot turn a paragraph into a path segment), and a duplicated trailing document extension is stripped when the value backs `%t` or `%s`; otherwise there is no post-processing or truncation, because the model is trusted to pick the most important words. The word budget is enforced through the prompt wording, while the vendor token limit reserves headroom for both a reasoning model's hidden chain of thought and a full recovered title. Cache lookups and keys follow the persistent cache under `Configuration > cache`, and provider selection follows the `[description]` schema. Description and author results are content-keyed: the key is built from the unit's content identity (the full-content hash when deduplication computed one, otherwise the large-file fast-path fingerprint), not its path, so identical content at different paths shares one entry and the path is only a hint in the prompt. A prompt-schema revision joins the description settings hash so a change to the content/question framing, the delimiters, the ASCII-output instruction, or the metadata cap invalidates completions cached under the old contract (the rendered template alone does not capture them), and an output-normalization revision joins both the description and geocoder settings hashes so a change to the ASCII normalization invalidates values produced under the old mapping. When a document's format uses `%a` and its embedded metadata (EXIF, PDF, or container) carries no author, the worker also asks the same text description provider who the author is: the request uses a fixed built-in prompt (not the configurable description prompt), carries the file path and extracted text like a description request, and is cached under its own kind so it never collides with the description entry. The answer populates `%a`; an over-long answer is rejected like a description value, and a failure or an `unknown` answer leaves `%a` unset so the segment is omitted.

### Defaults

When neither configuration nor inference supplies a format string for a kind, the opinionated defaults apply:

| Kind | Default format string |
|---|---|
| `document` | `Documents/%a-%t.%e` |
| `photo` | `Photos/%Y-%m-%d-%H-%M-%S-%l-%s.%e` |
| `video` | `Videos/%Y-%m-%d-%H-%M-%S-%l-%s.%e` |
| `audio` | `Audio/%a-%t.%e` |
| `repository` | `Projects/%o/%n` |
| `archive` | `Archives/%Y/%m/%f` |

The media and document defaults name the target from metadata and keep the
original extension via `%e`. The repository and archive defaults preserve
the original name; the archive default adds a year/month nest dated from
the file's modification time. An archive has no embedded date metadata, so
date placeholders fall back to the always-available modification time
(a filename-embedded date wins when one is present), which for a
downloaded or extracted archive is effectively its acquisition date. This
is a deliberate choice over birth/creation time: birth time is absent on
some filesystems (where it would fall back to modification time anyway) and
historically mapped to the inode change time on older Rust toolchains, so
modification time is the one timestamp with uniform, predictable semantics
everywhere; a move preserves it, so a relocated archive never re-buckets on
a later scan.

### Examples

Config file:

```toml
[target_paths]
photo = "Pictures/%Y/%m/%f"
audio = "Music/%a/%Y/%t.%e"
```

`photo = "Pictures/%Y/%m/%f"` moves `~/Downloads/IMG_0001.jpg` to `~/Pictures/2024/03/IMG_0001.jpg`, keeping the original name via `%f`. `audio = "Music/%a/%Y/%t.%e"` renames `~/Downloads/Song Title.mp3` to `~/Music/artist/2024/song-title.mp3`, deriving the artist and title from ID3 tags and normalizing them per the sanitization rules (here the ID3 artist `%a` = `Artist` and title `%t` = `Song Title` are lowercased and hyphenated to `artist` and `song-title`).

CLI override:

```text
homelinter --target-path photo='Pictures/%Y/%m/%f' --target-path video='Videos/%Y/%m/%f'
```

Locations and descriptions:

```toml
[target_paths]
photo = "Pictures/%Y/%m/%l/%s.%e"

[geocoder]
enabled = true
service = "nominatim"
language = "en"

[description.image]
enabled = true
model = "<vision-model-name>"
```

With this configuration, `~/Downloads/IMG_0001.jpg` moves to `~/Pictures/2024/03/paris/sunset-over-the-river.jpg`: the location is reverse-geocoded by Nominatim to `paris` and the description is generated by the LLM as `sunset-over-the-river`.

## Configuration

Configuration contains all persistent preferences, including the scan root and hidden-file inclusion. `scan.root` and `scan.hidden` are ordinary configuration keys: a CLI invocation may seed them with `--root <path>` and `--hidden`, and the TUI/SPA edit them through the settings API, which writes the configuration file. If no scan root is set, homelinter uses the host platform's home directory.

### Precedence

The single preference resolution order (highest to lowest) is:

1. Runtime settings written through the API (including interactive-client controls)
2. Launch-time CLI options, folded once at startup
3. Config file values
4. Inferred values from system tools and home directory structure
5. Opinionated defaults

This same order governs destination format strings, config-file selection details below, and all other resolvable preferences. Because a runtime write is applied last, it beats a launch-time option for the same key; a running scan keeps the settings snapshot it was accepted under.

### Config File Resolution (highest to lowest precedence)

1. Path specified by the `--config <path>` option
2. The per-user configuration path for the host platform, typically `$HOME/.config/homelinter/config.toml` on Linux and macOS and `%APPDATA%\homelinter\config.toml` on Windows
3. The system-wide configuration path for the host platform, typically `/etc/homelinter/config.toml` on Linux and macOS and the Windows system-wide application-data location on Windows

The configuration files are merged from lowest to highest precedence with a deep merge: nested tables and mappings are merged by key recursively; all other values - scalars and arrays - are replaced by the higher-precedence value; and an empty table contributes nothing, so a higher-precedence file cannot wipe an entire lower-precedence table (there is no "replace this whole table" syntax in TOML, and none is implied). Under these rules, a user `[description.image]` entry composes with a system `[description]` base, a higher-precedence `document_extraction` entry replaces only the argv array for its format key, and `scan.exclude_paths` is replaced wholesale rather than unioned, allowing a higher-precedence file to drop a lower-precedence pattern; the built-in `scan.default_exclusions` set is merged on top of the resolved `exclude_paths` unless it is disabled. The same deep-merge semantics apply to `PUT /config`, which merges submitted values into the existing file rather than replacing it; in addition, a `null` value in the submitted document deletes the key from the merged file, which is how a form-based client resets an option to its default. The write is applied in place to the parsed TOML document (`toml_edit` in the model crate), never by re-rendering a value tree, so the file's comments, blank lines, section and key order, dotted keys, inline tables, multi-line strings, and scalar styling all survive a write and the on-disk diff is limited to the keys the client actually changed: an edited scalar keeps the leading whitespace and inline comment of the value it replaces, an edited array keeps its one-per-line layout and per-entry comments, a new key is appended to the end of its own section, an existing section keeps its position, a section the file does not have yet is appended after the existing ones (before any trailing footer comment), and a table the patch leaves empty is removed so a file never accumulates stub sections. An empty table in the submitted document contributes nothing, matching the merge rule above. The patched document is validated exactly as it will be written, the file is rewritten only when the result differs from what is on disk (a no-op save does not touch the file), and the replacement is atomic. When the target file does not exist yet, the write seeds the parsed document from the embedded `defaults.toml` dump (the same file the repository test validates) and applies the patch to it in place, so the first saved setting produces a self-documenting configuration whose only difference from the documented defaults is the keys the user changed; a save that would leave that seeded document unchanged writes no file at all, exactly as a no-op save of an existing file leaves it untouched. The seeded values are explicit and therefore pinned: a later release's changed default does not override a key the seeded file already spells out, and deleting the key restores the built-in default. A `POST /session/scan` accepts no per-scan configuration; a scan runs against the current effective settings. A missing explicitly requested config file or a malformed config file is an error; an absent default config file is ignored.

Resolution is implemented over an injectable search chain (`ConfigChain` in the model crate): the system-wide and per-user files below the explicit file. Production always resolves the host chain; the service accepts a chain override in `ServiceOptions` (like the home and app-data overrides) so embedded and test runs can supply an empty chain, keeping config-file behavior hermetic on hosts that have their own per-user configuration.

The repository-root `defaults.toml` is a faithful dump of the built-in defaults: it lists every configurable key with its effective default value, and loading it is behaviorally equivalent to supplying no configuration file at all. A test asserts both that equivalence and that every key is present, so the dump is updated alongside any default change; keys whose default is unset (API keys, `user_agent_contact`, `model`, `prompt`) appear commented with the effective value documented. The same file is embedded at build time (`DEFAULT_CONFIG_TEMPLATE`) and seeds a missing writable config file (see "Config File Resolution" above), so a further test asserts the embedded copy is byte-identical to the repository file.

### Configuration File Schema

The configuration file is TOML. The supported schema is:

```toml
[target_paths]
# Each key is an Asset Kind: document, photo, video, audio, repository,
# or archive. Values are destination format strings (see "Destination
# Path Format Strings") resolving to a path
# relative to $HOME or an absolute path; a value must contain at least one
# placeholder and name the target file. The original filename is optional
# (omit %f/%F/%n/%e to discard it and name the target from metadata).
document = "Documents/%a-%t.%e"
photo = "Photos/%Y-%m-%d-%H-%M-%S-%l-%s.%e"

[geocoder]
enabled = false
service = "nominatim" # "nominatim", "photon", "google", "mapbox", or "custom"
endpoint = "https://nominatim.openstreetmap.org"
api_key = "<optional-api-key>"
language = "en"
neighbourhood_cities = [] # city names whose %l uses the finer neighbourhood level
user_agent_contact = "<optional-contact-string>" # appended to the User-Agent; recommended for public services such as Nominatim

[description]
# Default provider used for content-modality kinds without an explicit
# per-modality entry; kinds without a content source (repository and
# archive) never use a description provider. A per-modality entry takes precedence, including
# enabled = false. LLM transport settings live directly on the provider
# entry; a per-modality entry inherits any unset key from this base section.
enabled = false
service = "ollama" # "ollama", "openrouter", or "custom"
endpoint = "http://localhost:11434"
model = "<model-name>" # required when the provider is enabled
api_key = "<optional-api-key>" # required by openrouter; sent as a bearer header
max_words = 4 # optional; maximum words in the generated description
# Optional prompt template; placeholder {words}; {{ }} for literal braces.
# Unset = built-in wording (documents recover the original title first and
# fall back to at most max_words keywords; other modalities use keywords);
# the full path (with the filename) and any extracted document text are always
# included; with text the content comes first and the question last.
# prompt = "Describe the file in at most {words} words"
max_image_dimension = 1024 # optional; longest side in px for photos, SVGs, and video frames (0 = no photo downscaling; SVGs retain a hard safety cap)
max_video_frames = 8 # optional; cap on representative frames sampled from a video (about one per second); must be positive
max_context = 32768 # optional; upper bound on the ollama context window (num_ctx) per request; must be positive
rate_limit_ms = 0 # optional; minimum ms between requests (0 = none)

# Optional per-modality overrides can be added as [description.text],
# [description.image], [description.video], or [description.audio].
# An explicitly disabled per-modality entry suppresses the default for that modality;
# an entry that only sets `model` re-specializes just that modality's backend.

[document_extraction]
# Per-format text extraction commands used to preprocess documents
# before description generation. Each value is an argv array; `{path}`
# is replaced by the absolute input path and must be a complete argument
# of its own; plain text is read from stdout. Commands are never interpreted by a shell. Defaults
# are selected at runtime from available tools, like fd; an empty
# array disables extraction for that format.
pdf = ["pdftotext", "-layout", "{path}", "-"]
docx = ["pandoc", "{path}", "-t", "plain"]
odt = ["pandoc", "{path}", "-t", "plain"]
epub = ["pandoc", "{path}", "-t", "plain"]

[duplication]
large_file_threshold = 104857600

[scan]
# Absolute, normalized directory to scan; unset (or null) = the platform home.
# root = "/home/you"
# Whether hidden files and directories are scanned; default false.
hidden = false
exclude_paths = [".cache/**", "build/**"]
# Bare extensions excluded from discovery at any depth, matched
# case-insensitively against the final extension (e.g. ["png"]).
exclude_extensions = ["png"]
# Definition of "hidden" on Windows only; ignored on Linux/macOS, where
# hidden always means dotfile names. "explorer", "attribute", or "dotfiles".
hidden_definition = "explorer"

[output]
format = "pretty" # "pretty", "json", or "toml"

[cache]
# The persistent metadata cache is stored in the platform's standard
# per-user application-data directory by default.
enabled = true

[limits]
# Bounds on external calls and tool output. Every value is optional;
# an absent value uses the implementation default, and the defaults are
# never infinite. Overrunning a limit degrades to the normal failure
# behavior (e.g. `%s` falls back to the filename stem) rather than stalling the scan.
provider_timeout_seconds = 300
provider_concurrency = 1
tool_timeout_seconds = 30
tool_stdout_max_bytes = 16777216

# config hash, so saving it never marks a batch stale. theme selects the web
```

**Secrets**: API keys for `geocoder` and `description` providers must never be written to logs or included in suggestions.

**Validation split**: Configuration validation distinguishes structural errors from readiness advisories. Structural errors, like an unknown placeholder, an invalid or unknown key (including per-modality description keys), an unknown service name, an explicitly empty value, a malformed extraction command, an empty exclusion pattern, or a zero limit, make the config unusable and are rejected everywhere (a 422 on `PUT /config`, a failed load at startup), regardless of how the config was produced. Cross-field readiness conditions, like an enabled provider missing a companion value(a `model` for an enabled description entry, an `api_key` for `google`/`mapbox` geocoders or `openrouter` descriptions, or an `endpoint` for the `custom` provider), or carrying a value its service ignores(an `api_key` for `nominatim`/`photon` geocoders or `ollama` descriptions), are reported as `warnings` rather than errors:the config still loads and scans proceed with degraded metadata(the affected placeholder degrades to its fallback: `%l` is omitted, `%s` to the filename stem) until the missing value is supplied. This keeps the file valid while a client edits fields one ata time:enabling a geocoder or description provider never transiently invalidatesethe config mid-edit, so field-at-a-time saves never fail validation. Warnings are surfaced in `GET /config`,the `PUT /config` response,andthe `config.updated` event asa `warnings` object(field path to human reason);the SPA renders them inline onthe scan setup page,and in the configuration view.

Schema rules:

- `target_paths` is an optional mapping from Asset Kind to destination format string. Resolved paths emitted in suggestions are always absolute. An unknown placeholder, a format string with no placeholder, a format string that resolves to an empty path, or a format string that ends in a path separator is a configuration error. A resolved destination whose final segment is empty is rejected at suggestion time and produces no move. The original filename is never appended implicitly. Values must not contain `~` or environment-variable references; such a value is a configuration error, consistent with the API's rejection of `~`, relative, and environment-variable path inputs. The operating system's permissions and execution safety checks remain applicable. See "Destination Path Format Strings".
- `description` is an optional provider configuration with optional per-modality overrides. The base `[description]` provider is the default for every content-modality kind (document, photo, video, audio); a per-modality override (`[description.text]`, `[description.image]`, `[description.video]`, `[description.audio]`) re-specializes one content modality (`text` for documents, `image` for photos, `video` for videos, `audio` for audio), so a vision model can be configured for images only while a cheap text model describes documents. `description.max_image_dimension` caps the longest side in pixels of photos, SVG rasters, and extracted video frames forwarded to a vision backend: the image header is probed for its dimensions first (a full decode is skipped entirely for an in-bounds photo), and a larger photo is then decoded, downscaled (aspect preserved, via the image crate's fast integer thumbnail downsampler), and re-encoded as JPEG before the request, so a 12 MP phone photo reaches the model as a ~1 MP image and the vision model processes far fewer image tokens - the dominant inference cost on CPU; a photo already within bounds is forwarded unchanged (no decode, no re-encode loss), an undecodable photo (e.g. HEIC, truncated) is forwarded raw, and `0` disables the cap. An SVG with an image-capable backend (ollama) has its `<text>`, `<title>`, `<desc>`, and accessible labels extracted and included as text alongside a PNG rendered by `resvg` on a provider cache miss; the SVG source and encoded raster are each capped at 20 MiB, filesystem image references are denied (embedded data URLs remain available), and raster dimensions are capped at 4096 px even when the configured cap is zero, while a parse or render failure degrades to the extracted-text prompt. A video with an image-capable backend (ollama) gets representative frames decoded on a provider cache miss with `ffmpeg`, about one per second and evenly distributed across `ffprobe`'s reported duration, thinned to at most `description.max_video_frames` (default 8; without a duration, ffmpeg's `thumbnail` filter supplies one representative frame), each downscaled under the same cap, and all sent through the same vision transport as photos; the provider timeout is multiplied by the number of frames actually sent (see `[limits]`). Because a multi-frame vision request exceeds ollama's small default context (4096 tokens) - a single 1024 px frame costs roughly 1034 tokens, so the default eight-frame video needs about 8.4k - the ollama transport sizes `num_ctx` from the request payload (one conservative allowance per image plus the prompt and completion budget), capped by `description.max_context` (default 32768; a text-only request keeps ollama's default). Raising the cap admits larger inputs; lowering it suits a small-context model. A missing `ffmpeg` or any extraction or decode failure degrades to the text-only prompt, exactly as an undecodable photo does (see "Tooling Strategy"). `description.prompt` (on the base entry or a per-modality override, falling back to the base then to the built-in default) is an optional prompt template rendered with the `{words}` (the effective `max_words`) placeholder; unknown placeholders are a structural error, and `{{`/`}}` escape literal braces. The full source path (which carries the filename) and any extracted document or SVG text are always included, so they need no placeholders, a custom template cannot omit them (referencing `{name}` or `{path}` is itself a structural error), ordinary photos and videos receive the path but no extracted text; SVG images may include extracted labels and raster content. A text-bearing request places the delimited `<document>` content first and the rendered question last (inside `<question>` delimiters, after the `Path:` block) so the model answers the question instead of the document; a request without text keeps the question first with the path after it. Every question (description and author alike) additionally carries a fixed printable-ASCII instruction (typographic dashes to hyphens, curly quotes to straight quotes, other symbols to plain ASCII equivalents), appended after the rendered wording so a custom template cannot omit it; the response is normalized regardless (see "Provider Output Normalization"). Only those four modality keys may be used as per-modality keys; any other key is rejected. A document whose format uses `%a` and whose embedded metadata carries no author is also asked of the same text description provider (with a fixed built-in prompt) to infer the author; the answer populates `%a` and a failure leaves it unset so the segment is omitted.
- `geocoder.enabled` defaults to `false`. `service` accepts `nominatim`, `photon`, `google`, `mapbox`, or `custom`; `endpoint` defaults to the service's public endpoint (see "Provider Plugins"), and `language` is an ISO 639-1 code that defaults to `en`, so locality names read in English regardless of the provider's locale; it is passed through to the provider and shapes the resolved name, so it joins the geocoder settings hash and therefore the cache key. `user_agent_contact` is an optional string appended to the User-Agent sent with geocoder requests (`homelinter/<version>` plus contact); it does not join the cache key, and is recommended for public services that require identification. When enabled, `api_key` is required by `google` and `mapbox`, ignored by `nominatim` and `photon`,and optional for `custom`. Missing required keys,ignored keys,and a `custom` geocoder enabled without an `endpoint` are warnings,not errors(see "Validation split"),so enabling a geocoder mid-edit never fails the save; `%l` is omitted until the provider works. `geocoder.rate_limit_ms` is an optional non-negative number of milliseconds that paces any service as an additional floor on its built-in pacing: the effective interval is `max(built-in, rate_limit_ms)`, so it can only slow requests down. For `custom`, which has no built-in pace, it starts from zero. A `custom` service implements the neutral reverse-geocode contract described under "Provider Plugins". `geocoder.neighbourhood_cities` is an optional list of city names and controls how much of the provider's structured address is rendered into `%l`. By default `%l` renders the settlement (city, town, village, hamlet, or municipality) and falls through to the state/province/county and then the country when the provider does not populate it, and finally to the provider's free-text display name, so a provider that returns only free text still fulfills `%l`. When the provider's city component matches an entry (case-insensitive, trimmed), the finest level the provider supplies (quarter, suburb, district, or neighbourhood) is used instead: the intent is that frequently visited cities read at neighbourhood level while trips away from home read as a recognizable city name. Localities are resolved deterministically from the provider's structured address at cache-write time; no LLM is involved. A location is a property of the coordinate, so the geocode content key is only the signed latitude and longitude, and `geocoder.neighbourhood_cities` (which shapes the resolved locality) joins the geocode settings hash, so a change to either re-resolves locations (see "Cache Implementation"). The city list is hashed in a canonical form - trimmed, lowercased, deduplicated, and sorted - because matching ignores order, surrounding whitespace, and case, so a cosmetic edit does not needlessly re-resolve every coordinate.
- `[limits]` bounds external work. `provider_timeout_seconds` (default 300) caps each provider request; for a vision request carrying several video frames it is multiplied by the number of frames actually sent, since each frame costs roughly one inference. `provider_concurrency` (default 1) is the number of provider requests the background worker keeps in flight at once, so a backend that supports parallel inference (for example a local Ollama with `OLLAMA_NUM_PARALLEL > 1`) can work on several units at a time while per-provider rate limits are still honored; a value below 1 is a structural error. `provider_concurrency` is execution-only and does not join any cache key.
- `document_extraction` is an optional mapping from document format (`pdf`, `docx`, `odt`, `epub`, and any other format key) to an argv array. The first element is the executable and subsequent elements are arguments; the literal `{path}` must occur exactly once and must be a complete argument of its own (an argument that embeds `{path}` with other text is a configuration error), and the standalone argument is replaced by the absolute input path. Commands are executed directly without a shell, so paths and metadata cannot inject shell syntax. An empty array disables extraction for that format. A command with no executable, more than one `{path}`, an argument that embeds `{path}` with other text, or any unsupported placeholder is a configuration error. Defaults are selected at runtime from available tools, following the fd pattern: `pdftotext` for PDF, `pandoc` for office and ebook formats (the runtime default argv mirrors the shipped `defaults.toml` entries). When no external tool is on the PATH, in-process readers run as the final fallback (`pdf-extract` for PDF; native zip/XML readers for docx/odt/epub - see "Tooling Strategy"), so an unconfigured install still extracts text without external tools. External commands run with a bounded timeout and stdout size limit governed by `[limits]` (`tool_timeout_seconds`, `tool_stdout_max_bytes`), receive a minimal sanitized environment, and are terminated if they exceed either limit; the built-in readers apply the same stdout cap and refuse oversized files, so both paths fail identically. Non-zero exit status, timeout, output-limit failure, unavailable tools, or a failed or unsupported built-in read are treated as extraction failure; the description service receives no text and `%s` falls back to the filename stem while analysis continues.
- Deduplication always uses SHA-256 for both fast-path and full-content hashes. The hash algorithm is fixed and is not configurable.
- `duplication.large_file_threshold` is a non-negative integer number of bytes and defaults to `104857600` (100 MiB).
- `scan.exclude_paths` is an optional array of host-platform glob patterns applied to primary discovery in addition to the built-in defaults described under `scan.default_exclusions`; a pattern the user adds is never a replacement for the built-ins. A leading `!` marks a re-inclusion exception: `!build` cancels the built-in `build` exclusion while leaving the other built-ins in force. The name after `!` must be exactly one of the built-in directory names; any other `!` entry is a structural error, so a mistyped exception is rejected rather than silently ignored. An exception cancels only a built-in, never a positive pattern the user also lists. A pattern without a path separator matches the final path component at any depth, so `node_modules` excludes every such directory below the scan root. It does not exclude the home-wide symlink repair pass. Each pattern is evaluated against the normalized absolute path of a discovered object, so matching is deterministic and independent of the discovery order. A pattern containing a path separator matches the relative path from the scan root to the object (for example `build/**` excludes `build` and everything below it, and `cache/vendored/**` excludes that subtree); a pattern without a path separator matches the final path component at any depth (so `*.hs` excludes every Haskell source anywhere under the root). Both `*` and `**` are supported: `*` matches within a single path component and never crosses a path separator, while `**` crosses component boundaries, including zero components; a trailing `/**` matches a directory and everything below it. Patterns are applied only to primary discovery and are never applied to the home-wide symlink repair pass or to repository internals, which are atomic units. VCS ignore rules never affect primary discovery. Excluding a directory excludes everything below it; directory symlinks are excluded along with what they would label, because their contents are never traversed anyway.
- `scan.default_exclusions` is an optional boolean controlling the built-in directory exclusions and defaults to `true`. The built-ins are the conventional dependency, cache, and build-output directories listed in `defaults.toml` and mirrored by `DEFAULT_EXCLUDE_PATHS`: `node_modules`, `vendor`, `.venv`, `venv`, `__pycache__`, `.pytest_cache`, `.mypy_cache`, `.ruff_cache`, `target`, `build`, `dist`, `.gradle`, `.m2`, `.next`, `.nuxt`, `.terraform`, `Pods`, and `DerivedData`. When true or absent, they are excluded wherever they occur below the scan root, together with the resolved `scan.exclude_paths`, de-duplicated; a user pattern is added, never replacing them, so adding a single exclusion still inherits the built-ins. Individual built-ins are overridden by name with a `!name` entry in `scan.exclude_paths` (see above), which is the fine-grained override, while setting `default_exclusions` to `false` drops every built-in at once and uses only the user's positive patterns, which is the coarse override. The built-ins avoid traversing reproducible dependencies and generated outputs, which are generally not personal files; broad conventional names such as `build` and `dist` may also be meaningful user directories, so a user who wants them scanned re-includes them by name (`!build`) or drops the built-ins entirely. They apply only to primary discovery, never to the home-wide symlink repair pass or to repository internals, which are atomic units.
- `scan.exclude_extensions` is an optional array of bare extensions (without a leading dot) that excludes files from primary discovery at any depth, in addition to `scan.exclude_paths`. Matching is case-insensitive against the file's final extension, so `["png"]` excludes `shot.png`, `PHOTO.PNG`, and `sub/deep/icon.Png` in one entry; a leading dot is tolerated and normalized (`[".png"]` is equivalent). A name with no final extension - including a dotfile whose only dot is leading, such as `.png` - is never matched, so this is a literal extension set rather than a pattern language (unlike `exclude_paths`, it is not a glob). An empty entry, a path separator, or a glob metacharacter (`*`, `?`, `[`, `]`) is a structural error. Like `exclude_paths`, it applies only to primary discovery, never to the home-wide symlink pass or to repository internals, which are atomic units, and it joins no provider cache key because it changes what is discovered, not how a request is shaped.
- `scan.hidden_definition` is a valid, persistent configuration key defining what counts as hidden on Windows only: `explorer` (default) - an object is hidden when it has the Hidden or System file attribute; `attribute` - the Hidden attribute alone; `dotfiles` - names beginning with a dot, matching Unix semantics. On Linux and macOS the key is ignored: hidden always means dotfile names (see "File Classification"). It is a definition of what hidden means, independent of whether hidden objects are scanned (`scan.hidden`).
- `output.format` defaults to `pretty` and accepts only `pretty`, `json`, or `toml`.
- The persistent metadata cache is enabled by default and is stored in the platform's standard per-user application-data directory. It stores successful geocoding, description, and author-inference results, cache keys, provider metadata, schema/version information, and timestamps. Failed, timed-out, or unavailable provider requests are not cached as successful results and may be retried on a later scan. A provider response is not refreshed while its complete cache key remains unchanged, ensuring that repeated scans produce the same user-readable location or description rather than renaming a file because an external response changed. Cache writes are atomic and concurrency-safe; a corrupt or incompatible cache is ignored or rebuilt without preventing a scan. Cache contents may contain extracted text, descriptions, locations, provider identifiers, and content-derived identifiers, so the cache is user data and must be protected with normal per-user file permissions. The cache must not store API keys or full source files. Cache invalidation and clearing are exposed through the CLI and service API.
- `description.max_words`, `description.max_image_dimension`, `description.max_video_frames`, `description.prompt` (effective template for the modality), and `geocoder.neighbourhood_cities` join the cache entry key (see "Cache Implementation"), so changing any of them invalidates cached descriptions and locations and triggers fresh provider requests. Execution-only values (`description.max_context`, `[limits] provider_timeout_seconds`, `provider_concurrency`, the tool caps) bound how requests run but do not join the cache key, because they do not change the result.
- `scan.root` and `scan.hidden` are persistent configuration keys. `scan.root` is an optional absolute, normalized directory path: a relative path, a `~` or environment-variable reference, or a non-normalized path is a structural error, and an unset value falls back to the host platform's home directory. `scan.hidden` is an optional boolean that includes hidden files and directories when true and defaults to false. Both are seeded from `--root` and `--hidden` at launch and edited through `PUT /config`.

- `ui.theme` is an optional string accepted as `dark` or `light` and defaults to `dark` when absent. It selects the SPA's color theme; the SPA reads it from `GET /session`, the header's sun/moon button flips it and persists it through `PUT /config`, and `homelinter web --theme` seeds it at launch. It changes presentation only, so like `ui.path_filter` it is deliberately excluded from the config hash and saving it never makes the running batch look stale.
- `ui.path_filter` is an optional string used by clients to persist UI state (the TUI and SPA path filter) through the settings path: the TUI re-applies it at launch and keeps it across scans, while its cycled type/kind/status/manual filters reset with each scan. It is deliberately excluded from the config hash, so saving it never makes the running batch look stale, and it is part of the documented schema only so the merge, validation, and write path stay uniform with every other key.

### Cache Implementation

The cache is implemented as a single SQLite database file (`cache.db`) in the platform's standard per-user application-data directory. The database uses WAL (Write-Ahead Logging) mode for atomic writes and concurrent-safe read/write access.

**Schema**:

- `meta` table: key-value pairs storing schema version, creation timestamp, and metadata. Keyed by text string; values are text.
- `entries` table: cached query results. Columns:
  - `cache_key` (BLOB, PRIMARY KEY): SHA-256 hash of the complete request input (see "Cache Key Construction").
  - `kind` (TEXT, NOT NULL): entry type (`geocode`, `description`, `author`, `filename_analysis`).
  - `provider` (TEXT, NOT NULL): provider identifier (e.g., `description:ollama:mistral` or `nominatim:openstreetmap`) plus a hash of provider-specific settings (backend, model name, endpoint URL, language code, per-modality overrides). Settings are hashed to ensure that config changes invalidate cached entries.
  - `input_hash` (BLOB, NOT NULL): hash of the content-derived input: the file's content identity (full-content hash, or the large-file fast-path fingerprint when no full hash was computed) for descriptions and authors, the signed latitude and longitude for geocoding. Used for diagnostics and index optimization; not used for cache lookup (the `cache_key` is the sole lookup key).
  - `value` (TEXT, NOT NULL): the cached result (location name, description, or analysis).
  - `created_at` (TEXT, NOT NULL): ISO-8601 timestamp of insertion.
  - Index on `(kind)` for discovery and stats queries.
- `metadata_overrides` table: user-saved manual metadata edits, keyed by content identity so an edit applies to identical content wherever it appears. Columns:
  - `content_key` (BLOB, NOT NULL): the unit's content identity (the full-content hash, or the sha256 of the path for an unhashed file), the same value that keys provider cache entries, so an override survives moves and applies to every copy of identical content.
  - `field` (TEXT, NOT NULL): which value is overridden (`location`, `subject`, or `author`).
  - `value` (TEXT, NOT NULL): the normalized user value. A blank or normalize-empty value deletes the row instead of storing an empty string, so "cleared" and "never set" are the same state.
  - `updated_at` (TEXT, NOT NULL): ISO-8601 timestamp of the last write.
  - Primary key `(content_key, field)`.

**Manual override precedence**: a saved override wins over every provider and embedded value for its field and is applied to the analyzed file before suggestions are generated (see "Provider Plugins > Manual metadata editing"). Overrides are user data, not cache results: `DELETE /cache` never touches them (see "Clearing and eviction").

**Cache key construction**:

The cache key is computed as SHA-256 of a canonical serialization of the request tuple: `(kind, provider_id, provider_settings_hash, input_hash)`. Each field is length-prefixed as an 8-byte little-endian integer followed by its content, ensuring unambiguous serialization. This composition guarantees that any change to the provider configuration or input invalidates the key and forces a cache miss, while identical inputs always produce the same key and therefore deterministic cache hits. The `input_hash` is content-derived and never based on the file name or path: descriptions and authors use the file's content identity, and geocoding uses only the signed latitude and longitude (the requested language, which shapes the resolved name, is part of `provider_settings_hash`). The file path is still sent to the model as an identity hint, so the first description or author answer derived for a piece of content is stored under that content's key and reused by every copy; a subsequent edit to the content changes the full hash and re-runs the provider.

**Concurrency**:

Multiple processes may access the cache simultaneously. SQLite in WAL mode permits concurrent readers and serialized writers. Ordinary inserts into `entries` are write-once (same key, same value): if a concurrent process has already inserted an entry, the second insert either succeeds (WAL serialization order) or fails with `SQLITE_CONSTRAINT`; both outcomes are safe because the value is identical. A lookup always reads the latest committed value. A per-suggestion metadata re-request needs stronger semantics (see "Provider Plugins > Offline request loop"): it deletes the affected unit's entries (`remove`, a single-row delete that is a no-op when absent) and writes its forced result with `replace` (`INSERT ... ON CONFLICT(cache_key) DO UPDATE`), so a superseded or concurrent request can never win with a stale write-once row.

**Version and corruption handling**:

On cache open, the implementation reads `meta.schema_version`. If the version is absent, newer, or incompatible with the current code, the entire cache file is replaced and rebuilt from scratch. The schema version is bumped whenever the key construction or value contract changes incompatibly (for example, when description and author keys moved from path-based to content-based), so superseded entries are dropped instead of lingering unreachable. If any operation raises `SQLITE_CORRUPT` or other unrecoverable errors, the cache file is replaced and rebuilding proceeds, ensuring the scan is never blocked. A corrupt or missing cache is treated identically: the scan proceeds with no cache hits, and new results are written to a freshly created file. Replacement is atomic: a fresh database is written to a temporary name in the same directory and renamed over the old file, so a concurrent process never observes a partially written cache.

**Clearing and eviction**:

`DELETE /cache` (and the `--cache-clear` CLI flag) clears all rows from `entries` and the schema metadata in a single transactional write; it never deletes the cache file, and it never deletes `metadata_overrides` rows, because a manual edit is user data rather than a provider result. Because SQLite WAL serializes writers, a clear is a transaction like any other: it is safe while another instance holds the file open, safe during a scan (a concurrent scan's later inserts simply repopulate entries after the clear), and safe on Windows, where an open file cannot be deleted. The end state is "cleared, then repopulated from anything written after the clear" - exactly the semantics a pre-scan clear wants. File-level deletion is reserved for the corrupt-or-incompatible rebuild path, where the replacement is atomic (a fresh database written to a temporary name, then renamed over the old one), so concurrent rebuilds last-wins safely. Eviction policies (LRU, TTL, size limits) are not implemented; the cache grows unbounded within filesystem constraints. Future enhancements may add configurable size limits and eviction strategies.

**Inspection**: `GET /cache` exposes the stored entries for the TUI and SPA cache viewers. It is read-only, paged with `offset`/`limit`, filterable by `kind`, and reports per-kind counts. The cache key and input hash are hex-encoded for display; the stored value is returned verbatim, so the viewer shows the same provider result a later scan would reuse. Because cached values may contain extracted text or descriptions, the viewer displays user data like the rest of the cache.

### Provider Plugins

Provider plugins are the single interface for external intelligence: LLM analysis, content descriptions, and reverse geocoding. Each plugin type defines a neutral request/response contract, and built-in backends translate that contract into a vendor's API. A provider failure (non-2xx status, timeout, malformed response) is not a scan error and never blocks a scan: the request is not cached, the scan continues with the placeholder's fallback, and the next scan retries. External calls run with a bounded timeout governed by `[limits].provider_timeout_seconds` (see "Configuration File Schema"); overrunning it is a provider failure like any other.

**Provider Output Normalization**: every provider value that becomes metadata (description and author completions, and the reverse geocoder's resolved locality) is normalized to printable ASCII (U+0020 through U+007E) before it is validated, cached, or returned. The normalization decomposes to compatibility form and drops combining marks, so an accented letter keeps its base (`Zürich` -> `Zurich`); maps typographic punctuation to its keyboard equivalent (curly quotes to `'`/`"`, the ellipsis character to `...`, en/em and other dash characters to `-`, bullets to `-`, middle dots to `.`, `©`/`®`/`™` to `(c)`/`(R)`/`TM`, currency symbols to their ISO code, arrows to `->`/`<-`/`<->`, `×`/`÷` to `x`/`/`, the minus sign to `-`); collapses any whitespace run to a single space; and replaces any remaining non-printable or non-ASCII character with a space, so an unsupported character can never join two words or survive into a destination segment. Control characters are thus removed by the same rule. A value that normalizes to nothing is treated as a provider failure (not cached), and the description and author metadata caps (24 words / 240 characters) are applied to the normalized value. The reverse geocoder applies the same rule to the resolved locality, so a name like `Zürich – Kreis 4` becomes `Zurich - Kreis 4`. The prompt assembly for description and author requests additionally appends a fixed instruction to answer in printable ASCII (see "Description providers"), so a cooperative model avoids the mapping entirely; the normalization is the enforcement, the instruction is a hint. Because the mapping changes cached values, an output-normalization revision joins both the description and geocoder settings hashes (see the cache-key discussion under `%s` and `%l`), so entries produced under the old contract are not reused.

**Offline request loop**: provider requests are executed on a dedicated background worker that shares no state with the scan phases and cannot block them. Before jobs are planned, saved manual metadata overrides are applied to the analyzed files (see "Manual metadata editing" below), and the planner skips any field that is overridden, so a user edit suppresses the provider request for that field. The scan enqueues jobs into a FIFO `JobQueue` (`ProviderJob`s carrying the kind, provider identity/settings hash, input, and the scan epoch) and marks the suggestions of units with outstanding jobs `metadata_pending`. User-requested refresh jobs are inserted ahead of queued scan work, but do not interrupt requests already in flight. The worker probes every dequeued job against the persistent cache before anything else: a hit resolves its unit immediately without occupying a provider slot or waiting on provider pacing, while only a miss waits for one of `[limits].provider_concurrency` slots (default one), so even at the default concurrency the only serial work is the misses themselves and a fully cached batch drains in one pass instead of one paced job at a time. Priority refresh jobs overtake queued scan work in both phases: they are probed first, and their misses start as soon as an active request frees a slot instead of waiting behind a pre-drained scan batch. A forced re-request skips the cache read by design. On a miss the worker extracts document text for a description or author job, per `[document_extraction]` (see "Tooling Strategy"), performs the request under the `provider_timeout_seconds` bound (multiplied by the frame count for a multi-frame vision request), and stores successes in the cache; only these calls are subject to the per-provider pacing described below. Both outcomes resolve a unit's pending count: once the last outstanding request of a unit resolves, its suggestion is updated in place by stable id - rebuilt with the collected provider values on success, kept with generated fallbacks on definitive failure, using the original filename stem without its extension for `%s`, and `metadata_pending` cleared (a rebuild that now says the file stays put removes the suggestion). A redundant duplicate is never planned for provider work, and a rebuild only ever replaces a move suggestion: the shared `id_for_target` space means a delete must survive any stray resolution for its unit untouched. The batch is re-validated at that point with the real metadata applied (pending suggestions stay excluded), so a collision that only appears once a provider value lands is rejected with a reason, and one that disappears no longer blocks the suggestion. Pending suggestions are excluded from execution (see "Session Model > Execution"). Each resolution also broadcasts a `suggestion.updated` event for the changed row (or `suggestion.removed` when the rebuilt move no longer applies) plus a `metadata.progress` event (`{"completed", "total"}`), and `GET /session` exposes the same pair, so every client can show how many of the suggestions that originally had provider requests have completed all of theirs. `GET /session` additionally reports the current batch's cache lookups as `cache_hits` and `cache_misses`: how many provider requests the persistent cache answered and how many had to reach the provider, reset when a scan plans its work so the pair describes the batch on screen rather than the life of the process. A forced re-request (an explicit refresh that discards the cached value) reads neither the cache nor these counters. The two counts are named rather than slashed because they are not a fraction of one another; the SPA and TUI headers print them as `cache: N hits, M misses` once either is non-zero, which makes a run that is not reusing cached metadata visible instead of inferable from provider load. Requests to the same provider are paced by that provider's minimum interval (see "Geocoder rate limiting and identification" under "Provider Plugins"; description providers have no built-in pacing but honor their optional `rate_limit_ms`); with `provider_concurrency` above 1 the request starts stay paced, but two requests to the same provider may be in flight at once, so a backend must tolerate that (the documented public rate is never exceeded, since pacing spaces the starts). Results carry the scan epoch that enqueued them; a result whose epoch no longer matches the current scan is dropped without touching the session, so a scan that is cancelled or superseded never receives stale provider updates. Provider jobs also carry the unit's re-request generation, and a result whose generation no longer matches the unit's current one is dropped the same way (see the next paragraph).

**Per-suggestion re-request**: a client can discard and re-fetch the provider metadata that shaped one move suggestion without a new scan (`POST /api/v1/suggestions/{id}/refresh`, the TUI's `m`, the SPA detail pane's fetch metadata button). The service bumps that unit's re-request generation, removes the unit's pending cache entries, re-plans its provider jobs from the current effective configuration, marks it `metadata_pending` again, and enqueues the jobs as a priority group ahead of queued scan work (without interrupting already-running requests); a forced job skips the cache read and writes its result with the cache's upsert (`replace`) path. The endpoint accepts an optional `clear_overrides=true` query parameter: when present, the service first plans against the effective values with every manual override cleared, and only if that planning yields a job does it delete the content's persisted overrides and the in-memory copy before marking the suggestion pending, so a user can return a manually edited field to provider resolution in one action. Clearing is part of the same guarded operation: a refusal (for example, no provider work even without the overrides) leaves the saved overrides untouched. A superseded job carries an old generation and is dropped on resolution by the generation check, so an in-flight request can neither resolve nor overwrite the current one. Only one re-request can be in flight per unit: a second re-request before the first one's jobs resolve is refused with a `409`, so two forced writes can never race over one cache entry (the generation check alone cannot order them, because a cache write happens before the generation check). The guard is per unit, so two different suggestions with identical content (which by design share one content-addressed cache entry) can still race that shared entry; the worst case is that the row keeps the earlier of the two fresh values, while each suggestion's own result stays correct. The re-request does not change the `metadata.progress` denominator: the unit already counted when the batch was published, so the total stays stable while the completed count dips back until the fresh request lands. The mutation, cache invalidation, event publication, and enqueue all happen in one session-locked step, so a new scan cannot replace the batch in between and leave this refresh publishing an old id or enqueuing epoch-stale jobs. A re-request is allowed only when the session is `ready` or `done` (the same guard as execute/export, so it cannot run against a scan or execution in progress) and only when re-planning actually yields a job: the unit's format must use a provider placeholder, a provider for that field must be enabled, the provider input must exist, and the field must not already be answered by a manual override or embedded metadata. Anything else (not ready, no batch, unknown id, a delete, a re-request already in flight, or no applicable provider work) is a `409` whose reason names the blocker - for example that the location and subject are set by manual overrides and which fields to clear - so a configured provider skipped because a user edit or embedded value wins is never misreported as a missing provider. A re-request does not perform a scan and does not regenerate the batch, so a suggestion whose rebuild now says the file stays put is removed exactly as a scan-time resolution would be.

**Manual metadata editing**: a client can save, replace, or clear the `location`, `subject`, and `author` values that shape one move suggestion without a scan and without a provider call (`PUT /api/v1/suggestions/{id}/metadata`; the SPA detail pane's metadata editor). The request body is a full replacement: each of the three fields is either a string or null/absent, where an absent, null, blank, or normalize-empty value clears that field. Every value is validated with the same completion contract as a provider value (the 24-word / 240-character cap) and rejected with a `422` otherwise. A value that normalizes to the provider's already-resolved value for that field is treated like a blank one: it is not pinned as an override, and an override saved earlier for that field is deleted, because the provider already supplies the same text. The service persists the surviving fields in `metadata_overrides` under the unit's content identity in the cache database, applies them to the analyzed file, and rebuilds the suggestion through the same `commit_unit_rebuild` path a provider resolution uses, so the batch is re-validated and the returned row already reflects the edit; a rebuild that now says the file stays put removes the suggestion and returns `{"item": null}`. The edit is allowed only from `ready` or `done` and only for a move suggestion (a delete has no editable metadata: its fate is decided by duplicate grouping, so a `409` is returned), and an unknown id (no batch context) is also a `409`. A manual edit does not clear `metadata_pending` when the unit still has provider work outstanding for a non-overridden field, so that in-flight request can still resolve and rebuild the suggestion without clobbering the edit (overrides win in the value precedence). Because overrides are keyed by content identity, an edit applies to identical content wherever it appears and survives a later scan, a move, and a `DELETE /cache`; a subsequent scan applies the overrides before planning, so the overridden files are never re-planned for those fields. Both the SPA detail pane and the TUI's metadata dialog use the endpoint (the TUI dialog opens with `M` and starts from the effective values, sending all three fields like the SPA). The returned suggestion's `manual_overrides` names the fields currently pinned by saved edits (omitted when none), and the session's `manual_overrides_total` counts affected suggestions, so clients can mark overridden rows and show a total without refetching every suggestion. The SPA's preview tab renders a `rebuild` action as an icon button after the destination path's copy button (`POST /api/v1/suggestions/{id}/rebuild`) that re-applies the effective metadata - including any override persisted for the file's content - and rebuilds the destination in place, without re-entering values or calling a provider. Because a batch yields at most one move suggestion per content group (identical content is otherwise a delete), its use is to force a fresh destination from the current metadata rather than to fan an edit out to sibling rows; identical content in a later scan still picks up the override when the scan applies overrides before planning.

**LLM providers** (`description.service`):

| Backend | Default endpoint | API key |
|---|---|---|
| `ollama` | `http://localhost:11434` | never required; a configured key is sent as a bearer header |
| `openrouter` | `https://openrouter.ai/api/v1` | required (config error when LLM enabled without it) |
| `custom` | user-supplied | never required; a configured key is sent as a bearer header |

Each backend adapts a neutral completion request (the rendered prompt template, the configured `model`, with the word budget mapped to a vendor token limit) to its vendor's API and normalizes the returned completion text into the neutral response. The `ollama` and `openrouter` backends translate into the vendor's native chat-completions schema; the token limit is `max_words * 4 + 1024`, reserving headroom for a reasoning model's hidden chain of thought (which counts against the same completion budget) alongside the answer, so a thinking model can reason and still emit a value, and the context window (`num_ctx`) is sized from the payload and capped by `description.max_context` so a multi-frame vision request is not rejected by ollama's default. `max_words` itself is enforced by the prompt wording, not the token limit. Reasoning normally stays in the vendor's separate channel (ollama's `thinking`, OpenRouter's `reasoning`), so only the answer is read; any inline chain-of-thought tags left in a completion are stripped before it is used, every completion and the resolved geocoder locality are normalized to printable ASCII (see "Provider Output Normalization"), and a description or author completion over the 24-word/240-character metadata cap is rejected as a provider failure so prose cannot become a path segment (geocode values are structured and are not length-checked). They do not send the neutral contract on the wire. The neutral contract is what a `custom` backend (and any local gateway speaking it) implements: `POST` to `endpoint` with JSON `{"model": "...", "prompt": "...", "max_words": N}` where N is the effective `[description].max_words`, and a successful response is `{"content": "..."}`. An optional configured `api_key` is sent as an `Authorization: Bearer` header. Servers speaking the neutral contract (including local gateways such as LM Studio) work through the `custom` backend. New LLM vendors are added behind the same interface.

**Description providers** (`[description]`):

Description providers are LLM providers; their transport settings - including the optional `prompt` template rendered with `{words}` (built-in wording when unset; the full source path and any extracted document text always included, with text placed before the question) - live directly on the `[description]` entry (or the per-modality override), with per-key fallback to the base entry. Hosted APIs (openrouter) throttle by requests per minute on free tiers and local models can stall on concurrent calls, so an entry can set an optional `rate_limit_ms` minimum interval between request starts of that provider on the worker, mirroring `geocoder.rate_limit_ms` (description backends otherwise have no built-in pacing; `0` means no delay; requests to one provider are spaced by this interval but, when `[limits].provider_concurrency` is above 1, several can be in flight at once).

**Geocoder backends** (`[geocoder]` `service`):

| `service` | API | default `endpoint` |
|---|---|---|
| `nominatim` | OpenStreetMap Nominatim reverse geocoding | `https://nominatim.openstreetmap.org` |
| `photon` | Photon reverse geocoding | Photon default host |
| `google` | Google Geocoding API | Google default host |
| `mapbox` | Mapbox Geocoding API | Mapbox default host |
| `custom` | neutral contract (below) | user-supplied |

Each backend maps a neutral reverse-geocode request (latitude, longitude, optional `language`) to the vendor API and parses its structured address into a neutral locality (`fine`/`city`/`region`/`country` plus a free-text fallback). The neutral contract is `POST` to `endpoint` with JSON `{"latitude": ..., "longitude": ..., "language": "..."}`; a successful response is `{"name": "..."}` and may additionally carry optional `neighbourhood`, `city`, `region`, and `country` fields that take precedence over the free-text `name` when present. Raw coordinates are never interpolated into paths; the selected locality fulfills `%l`.

**Geocoder rate limiting and identification**: requests to a geocoder backend are paced so request starts are at least the documented interval apart, never faster than the provider's policy, and are handled by the background provider worker (see "Provider Plugins > Offline request loop") so the scan itself never waits on them. The built-in public services enforce their providers' usage policies: `nominatim` sends at most one request per second and `photon` its documented public rate, so a first scan over many GPS-tagged photos trickles rather than floods the public endpoint; the pace is applied between request starts of the same provider on the worker. Requests identify with a User-Agent of `homelinter/<version>` plus the optional configured contact (`geocoder.user_agent_contact`), as public geocoding services require. `custom` and self-hosted endpoints are the user's responsibility and get the same serialization with no built-in delay unless the optional `geocoder.rate_limit_ms` is set (in milliseconds), which paces them exactly like the built-in public services pace themselves. The setting applies to every service as an additional floor on its built-in pace (`max(built-in, configured)`): a value below the built-in pace is absorbed, a value above it only slows requests further, and the documented public pace can never be exceeded. Rate delays and timeouts compose: a request that overruns `[limits].provider_timeout_seconds` is a provider failure like any other.

## User Interfaces

The service is the only backend. It owns the scan session, configuration, suggestion generation, batch validation, execution, export, and reporting. The CLI, TUI, and SPA are clients of the service and do not implement filesystem operations independently.

The scan root and the hidden-file selection are ordinary runtime settings in every client: CLI options (`--root`, `--hidden`) seed the initial effective settings, and the interactive clients edit them through the settings API, which persists them to the configuration file. A running scan keeps the settings snapshot it was accepted under.

The CLI and the TUI embed one service instance in the same process: they bind a loopback listener on an ephemeral port, build the service in-process, and drive it through the HTTP API described under "Service API > Client Lifecycle". Managed sessions always end with `POST /api/v1/shutdown` followed by a bounded wait and, if the service does not exit promptly, forced termination, so an invocation-owned service never outlives its client. The standalone `web` command serves on an ephemeral port, prints the readiness line `homelinter: listening on 127.0.0.1:<port>` to stdout, and never shuts itself down; it is terminated explicitly. The client contract itself is process-agnostic: a future external client can spawn the same binary and parse that readiness line.

The `web` command launches the same service as a standalone localhost server on an ephemeral port. It remains running after browser disconnects and is terminated explicitly by the user. The SPA communicates with it through REST and Server-Sent Events. The server is localhost-only, unauthenticated, and keeps session state in memory; a restart requires a new scan.

All clients display the same suggestions and previews. Interactive clients may select top-level suggestions, while dependent operations are included automatically. Filtering affects navigation and bulk selection only. The full-screen review experience lives in `homelinter tui`; the plain CLI scans, prints a summary, and points the user at the TUI or the `--execute`/`--export` actions (see "Command-Line Interface Schema"). The TUI requires a terminal of at least 80x24 and refuses to start on a smaller one.

### CLI (Command-Line Interface)

The CLI uses the service lifecycle defined above and supports two modes:

- **Plain scan mode (default)**: scans the selected root, generates suggestions, and prints a summary pointing the user at `homelinter tui` for full-screen review or at `--execute`/`--export` to act without review. It never acts on its own; nothing is executed or exported unless one of those flags is given. See "Command-Line Interface Schema" for the exact flow.
- **Non-interactive mode**: driven by instructions passed as command-line arguments, such as `--execute` or `--export`. These modes run to completion without prompting.

### TUI (Terminal User Interface)

- Full-screen interactive terminal interface built with `ratatui` and `crossterm` (target visual style: ASCII only, no em-dashes or special glyphs).
- Uses the shared service and its standard client lifecycle, including `POST /api/v1/shutdown` on quit.
- Displays suggestion previews and supports filtering and selection of top-level suggestions.
- Requires a terminal with minimum 80x24 dimensions.

Implemented as the `tui` subcommand of the CLI binary (see "Command-Line Interface Schema"), embedding the service in-process exactly like the CLI flow. Screens: a scanning progress view, an editable scan-settings form, a two-pane suggestion browser (filtered list plus detail panel), a live execution log, a report view, a configuration view, and a metadata-cache viewer. The scanning view keeps one row per `scan.progress` phase, like the SPA: each row shows a fixed-width meter on the left and `phase (detail)  scanned/total, elapsed=Ns` on the right, with the detail naming the worker filling the phase (for example the extractor behind `metadata`) omitted when absent and `scanned=n` shown without a total for phases that cannot know theirs. A phase identified by the same name updates its row in place, so the service's one-second heartbeat never appends duplicates; an event for a new phase marks the previous row complete and appends the new active row, and a phase returning after other phases ran in between starts a fresh row (metadata extraction, repository scans, and the hashing pass all run inside one analysis loop). A completed row is frozen at its last counts with a full 32-cell ASCII track (`#` for work done, `-` for the rest) labelled `100%`; an active row with a total fills to the phase's fraction and shows the whole percentage, while a phase that cannot know its total (the two walks and the hashing confirmation pass, plus the moment before the first event arrives) bounces an eight-cell segment back and forth along the track, never wrapping past an end. The segment's position comes from the event's own `elapsed_ms`, or from the frame clock before the first event arrives, so the heartbeat animates it without the screen holding a timer of its own. The browser's row labels render `name -> dest` with paths relative to the scan root, verbatim up to three segments and ellipsis-truncated to the last three beyond that, matching the SPA's rule; a suggestion whose provider metadata is still in flight renders as an animated `scanning <filename>` row instead; a move with saved manual overrides ends with a ` [manual]` badge. The detail panel shows id, type, kind, status, target, new path, reason, dependents, rejection, the effective `location`/`subject`/`author`, and the overridden field names, plus the `metadata`/cache progress label. While provider requests are outstanding the browser header and the scanning screen show one combined progress label, `metadata: completed/total, N hits, M misses`, where the cache half appears once the batch has checked the provider cache at all and a half with nothing to report is omitted; the header also carries the session's `manual_overrides_total` as `manual: N`. It keeps one `GET /events` Server-Sent Events connection as the fast path for live events, and polls `GET /session` every frame as a backstop so the session state stays honest even when the stream is dropped.

Command key map (see `tui.rs`): arrows and `j` to move; PageUp/PageDown to page; space to select; `a` to select all filtered and `A` to clear the selection of suggestions matching the active filter (a selection made under another filter survives, like the SPA's `clear filtered`); `t`/`k`/`u` to cycle type, asset-kind, and status filters; `f` to cycle the metadata filter (all/manual/auto); `/` to edit the path filter (a case-insensitive substring over each suggestion's full absolute source target, move destination, and duplicate-keeper paths, shown in the footer's filter line and truncated for display; an empty value clears it); `c` to clear all filters; `m` to re-request provider metadata (when the row has saved overrides, a confirmation first names them and, on `y`, calls the refresh endpoint with `clear_overrides=true`, matching the SPA's confirm modal; otherwise the plain refresh is used); `M` to open the manual metadata dialog for the highlighted move, edit `location`/`subject`/`author` (Tab/Up/Down switch fields, Enter saves through `PUT /suggestions/{id}/metadata`, Esc cancels; blank fields clear the override, and a save that makes the file stay put removes the row); `b` to rebuild a move's destination from the effective metadata; `x` to execute with a confirmation dialog; `e` to export to a script path; `n` to open the editable scan-settings form; `g` to view the read-only configuration; `v`/`l` to open the cache viewer; `C` to clear the cache after confirmation; `?` for help; `c` during a scan or run to cancel the in-flight work and stay in the suggestion browser; `q`/Esc/Ctrl-C to quit (cancelling in-flight work first). Like the SPA, a batch whose `batch_config_hash` no longer matches `config_hash` raises a stale-suggestions dialog before execute or export, offering proceed-anyway (`y`), re-scan with the current session settings (`r`, discarding the pending action), or cancel (`n`/Esc).

The scan-settings form (`n`) seeds every field from the service's live `GET /config` and edits the durable configuration: root, hidden files, scan exclusions, one destination override per asset kind, geocoder and description provider transport, duplication threshold, limits, the cache toggle, and per-format document-extraction commands. Enter edits or toggles one field, Tab/arrows move, and `s` saves the minimal partial document through `PUT /config` (blank optional values are sent as `null` to delete the key and restore the built-in default; a blank extraction command does the same and `-` disables that format); API keys are write-only, so typing one stores it and leaving the field blank keeps the saved key. A successful save re-reads the configuration, then starts a scan against it; a failed save leaves the form open with a toast, and starting a scan never writes settings silently. The path filter is client UI state persisted to `[ui].path_filter` (see "Configuration File Schema") through the same settings path: it is re-applied when the TUI launches and kept across scans (so the auto-started first scan is already filtered), while the cycled type/kind/status/manual filters reset with each scan, and `c` clears everything including the saved path filter; a failed save keeps the live filter and only loses the value for the next launch.

### GUI via SPA (Single-Page Application)

- The SPA is served by the standalone `web` service described above.
- It can view and modify live configuration; configuration changes are persisted by the service.
- It communicates through REST and Server-Sent Events.
- It is localhost-only, unauthenticated, and survives browser disconnects; closing the browser does not stop the service.

Implemented under `webui/` as React + TypeScript + Vite, with no client-side router (one page, internal views like the TUI). The typed API client (`webui/src/api.ts`) mirrors the Service API JSON shapes from `crates/model`; pure logic lives in `webui/src/lib/` (`filter.ts` filters, `format.ts` path/shorten/count helpers, `native.ts` desktop directory-picker bridge, `report.ts` execution-report text, `sse.ts` SSE payload parsing, `toasts.ts` transient-notice merging, and `modal.ts`'s Escape-dismissal stack, whose stack logic the node tests cover while its document listener is thin glue) and is unit-tested with Vitest in a node environment (no DOM required). The palette is defined once as CSS custom properties, with dark as the default and an optional light palette that keeps the same signal meanings (green done, red rejected/failed, amber partial/busy) at accessible contrast; the header's sun/moon toggle switches the `data-theme` attribute and persists the choice through `PUT /config` as `[ui].theme`, while the session's `theme` field applies the saved choice on load. Components render with plain CSS classes and a sans-serif UI typeface (a system font stack), reserving a monospace stack for machine-readable content such as file paths, code, config documents, and cache hashes (in the detail preview the `from`/`to`/`target`/`original` labels and the rejection reason use the sans stack, while the path text and its copy action stay monospace); the windowed suggestion list applies its dynamic row geometry through the CSSOM (`element.style` assignments), which the strict Content Security Policy (`script-src 'self'`, `style-src 'self'`, with `frame-src` opened to `https://www.openstreetmap.org` solely for the suggestion detail pane's embedded map preview) permits, unlike inline style attributes in markup; the Vite build disables the modulepreload polyfill so `index.html` carries zero inline scripts. The SPA keeps one `EventSource('/api/v1/events')` stream with the browser's built-in reconnect as the fast path for live events, plus an unconditional `GET /session` poll every 2 seconds that refreshes the session object (state, config hashes, counts) and keeps the UI honest when the stream is interrupted or another client changes the configuration. State transitions mirror the TUI's phases: scan form, progress, suggestion browser with filters and selection, live execution list, report, and a configuration view. The SPA's suggestion browser is a single selectable list, unlike the TUI's two-pane browser: rows open with a checkbox on the left, and the rest of the row renders as one-line action sentences - `move <path> to <path>` for moves and `delete <path>, duplicate of <path>` for duplicate deletes (the retained keeper read from the suggestion's `duplicate_of` metadata) - with no status suffix: a finished row carries its outcome as the row text's own colour instead (`rowTone` in `format.ts`), using the same palette as the run list - a done (`executed`) row in the ok green with the whole sentence struck through, rejected and failed rows in the bad red, a partial row in the busy amber, and a skipped row dimmed - while a rejected row still appends its `[rejected: ...]` reason and a metadata-pending row shows the scanning placeholder. A done suggestion's checkbox is cleared and disabled: its execution removes it from the selection (see "Execution policies"), so a finished action cannot be re-selected or executed again. While provider requests are outstanding, the suggestion browser shows one combined label in a full-width activity strip directly above the list, `metadata: completed/total, N hits, M misses`, built by `metadataProgressLabel`, and the scanning view shows the same label inline; the label sits next to the rows whose metadata it is filling in, and the strip carries a slim progress bar for the `completed/total` half. The scanning view's state line reads `scanning ...` above a stage list: each `scan.progress` phase that has started is one persisted row (`ScanStages`, fed by `appendScanStage` in `format.ts`), with the meter on the left - a fixed-width track, identical in every row so the bars align - and the phase's description on the right, rendered through `scanProgressLabel` as `metadata (exiftool) 4312/11263, elapsed=12s` - worker detail included when the event carries one, `scanned=n` without a total for phases that cannot know theirs. The latest, still-running row is visually dominant: its label and percentage render in bright white (`--bright`), while completed rows and the unstarted placeholder stay dim. Stages are identified by phase name only, so the service's one-second heartbeat, which re-publishes the last phase, updates the active row in place instead of appending a duplicate, while an event for a new phase marks the previous row complete - completion is inferred from the transition because the service sends no per-phase completion event - and appends the new active row at the end; a phase returning after other phases ran in between (metadata extraction, repository scans, and the hashing pass all run inside one analysis loop) starts a new row. A completed row stays frozen at its last reported counts with a full bar labelled `100%`, so the history of the scan stays on screen and the elapsed clock keeps advancing while a phase reports nothing; a determinate row fills its bar to the phase's fraction and labels it with the whole percentage (`scanProgressFraction`/`scanProgressPercent` in `format.ts`), and an indeterminate row - the two walks, the hashing confirmation pass, and the moment before the first event arrives, which is why the list opens with one placeholder row - bounces a fixed-width segment back and forth along the track (`.scan-meter-bar.indeterminate`, an alternating CSS animation, slowed under `prefers-reduced-motion`, and never wrapping past an end), so a long extraction pass shows per-second movement instead of a frozen line. The cancel button sits once in the scanning header beside the `scanning ...` label rather than inside any stage row, so every row is the same height and cancelling is one stable target instead of a button that moves as rows complete. The scanning view is never hidden behind the scan setup form: a scan already in flight - whether the user just started it, the window was opened or reloaded mid-scan, or another client started it - moves the SPA to the progress view from the first `scan.progress` event (with the unconditional `GET /session` poll as a backstop), clearing an open setup form, so the live stage list and the cancel button are always reachable; the run view renders only the execution list and its report, so a scan progress line never leaks into a run. The cache half comes from the session's `cache_hits`/`cache_misses` (refreshed by the 2-second poll) and appears once the batch has checked the provider cache, a half with nothing to report is omitted, and the whole strip disappears when both halves are empty. Row paths are displayed relative to the scan root: a relative path of at most three segments is shown verbatim, and a longer one is truncated to its last three segments with an ellipsis prefix (`.../2024/03/IMG_1.jpg`); a path outside the scan root (possible for destinations) falls back to the absolute path under the same truncation rule, and the detail pane always shows the full absolute paths, each as a clickable path with an inline copy-icon button at the end of the path, both copying the full path to the clipboard (the async Clipboard API, with a hidden-textarea `execCommand` fallback); the icon briefly swaps to a check on success. The list is windowed with `@tanstack/react-virtual`: only the rows in and around the viewport are mounted, with a fixed row height, so a batch of hundreds of thousands of suggestions never becomes a DOM tree of that size, and each row is memoized so a checkbox toggle or a single provider-metadata update only reconciles the affected rows. The rows themselves are also fetched a page at a time through the service's paged `GET /suggestions?offset&limit`: the SPA fetches the first page (500) when it enters the browser or the filter changes, appends the next page as the user nears the bottom of the loaded window, and keeps the server-reported filter total as `suggestionsTotal` to bound the append-as-you-scroll paging. The `suggestion.batch` event therefore only signals the batch total, and a filter change resets to the first page. The five filter dimensions are the four unlabeled native `select` combo boxes (type, asset kind, status, and metadata), each listing every value with an unconstrained entry first - `move or delete` for the type filter, `any type` for the kind filter, `any status` for status, and `auto or manual` for metadata - so a value is chosen in one click or keystroke instead of being cycled through, with each select carrying an `aria-label` naming its dimension (the status combo's entries and its closed control take the suggestion rows' outcome colours - green `done`, red `rejected`/`failed`, amber `partial`, dim `skipped`, plain for `any status`/`pending` - so the filter reads like the rows it keeps), plus a `path filter` text input (`aria-label="path filter"`): its committed value (debounced roughly 250 ms while typing, Escape clears, and an overlaid `x` clear button appears inside the input's trailing edge whenever it holds text, clearing the filter and returning focus to the input) filters suggestions by a case-insensitive substring over the full absolute source target, move destination, and duplicate-keeper paths, never the truncated display form, so a hit is never hidden by row truncation and the client-side predicate matches the server-side filter. The whole filter round-trips through the page URL's query parameters (`type`, `kind`, `status`, `manual`, `path`; unconstrained dimensions are omitted, so a fully cleared filter produces no query string): the SPA seeds its initial filter from the URL at load, writes every change back with `history.replaceState` (there is no router, so no history entries or popstate handling), and a reload or a shared link lands on the same filtered view. The `reset` button next to them is disabled while no dimension is constrained. Every `select` in the app, its drop-down list included, is painted from the active theme palette: the `color-scheme` declaration only asks the browser for widgets matching the theme, while the platform draws the option popup itself and on a light GTK theme rendered it light under the dark theme's light text, so `select` and `select option` carry explicit background and text colours. The kind filter's choices cannot be derived from a single page, so they come from `GET /report/summary`'s `suggestions_by_kind`. Provider-metadata deltas (`suggestion.updated`/`suggestion.removed`) are coalesced into one animation-frame batch before they are applied, and each delta is checked against the active filter: a resolved row is only appended when it matches, and a row an update pushes out of the filter (for example a pending row that re-validates to rejected) is dropped, so the streamed window never shows rows the server-side filter excludes. Bulk `select filtered` adds every suggestion matching the active filter through the service's filter-based `POST /selection/add` instead of shipping every id (done suggestions are never added: every selection path skips them, so a finished action cannot come back as selected), and `clear filtered` removes exactly the filter-matching suggestions through the filter-based `POST /selection/remove` (with no dimension constrained, that clears the whole selection), so a selection made under a different filter survives both buttons; both actions optimistically apply the same predicate to the loaded window and re-sync from the service on failure, and the `N selected` count beside them reports the session's whole selection, not just the matching rows. `execute` and `export` stay disabled until the session can act (`ready` or `done`) and the selection is non-empty, and the disabled tooltip names whichever precondition is missing. The two committing actions are the only filled buttons in the app, so their weight is unmistakable: `execute` is the red caution action (`button.caution`) and the scan form's `scan` button is the green go action (`button.go`) that starts it. Ticking the checkbox is the only way to change selection (a done row's checkbox is disabled); clicking the row body opens a detail pane on the right (it does not toggle selection) with three tabs: preview, location, and metadata. A divider between the list and the detail pane can be dragged to resize the pane (or moved with the arrow keys when focused), clamped so both panes keep a usable minimum width and hidden when the panes stack on a narrow viewport. The preview tab renders a browser-native file preview when possible: images use an image element, video and audio use media controls, PDFs and text-like files use an embedded frame. When a preview exists, the tab bar also offers an enlarge icon that opens the same media in a full-screen modal (dismissed by its own `x` close button, a click on the backdrop outside the media, or Escape); the location tab carries the same enlarge icon while it is active, opening the embedded map in that modal instead of the media, so a map can be inspected full screen without leaving the pane. One modal state serves both, so only one can be open and Escape dismisses whichever it is. The service exposes these previews only through a same-origin, suggestion-id-based endpoint with an extension allowlist. The endpoint resolves the preview source from the suggestion's execution state rather than blindly reading the target: an executed (or partially executed) move previews the destination where the file now lives, an executed duplicate delete previews the retained keeper (`duplicate_of`, which execution keeps pointing at the keeper's current path even when the keeper itself was moved in the same batch), and every other suggestion previews its own target; each post-execution candidate falls back to the target if it is unreadable, and a not-found for a still-unavailable post-execution path reports `preview file is not available` (the same message as a missing target), so the SPA can keep rendering the preview element chosen by the same rule (`previewSourcePath` in `webui/src/lib/preview.ts`) without distinguishing the two failures. Unsupported file types still show the proposed action - the source and destination paths for a move, or the deleted target with its keeper shown and labeled `original` for a duplicate delete. Move suggestions carry no generic `reason` sentence in the preview (the `from`/`to` paths already state the operation). A rejected suggestion additionally renders its complete `rejection_reason` in the preview, since the list row only carries a short truncated form. The location tab appears only when the suggestion carries GPS coordinates: it shows the coordinates, the reverse-geocoded place name when reverse geocoding succeeded, and an embedded OpenStreetMap map preview. The metadata tab is always present for a move suggestion: it renders any file or provider metadata beyond the keeper pointer (EXIF fields like camera, date taken, author; file info like size, bitrate, duration, page count) as a table, and below it a manual editor with `location`, `subject`, and `author` inputs prefilled from the effective values. Saving the form calls `PUT /suggestions/{id}/metadata` (blank inputs, or a value matching the provider's resolved value, clear the field) and the row is replaced with the rebuilt suggestion; a saved value is keyed by content identity, so it applies to identical content everywhere and survives a re-request, because a manual override wins the value precedence. The editor is disabled while the suggestion is pending, and a save that makes the file stay put removes the row with a toast. For a delete suggestion the tab is shown (read-only) only when the suggestion carries metadata, since a delete has no editable fields. A row whose metadata carries a saved manual override ends with a compact `manual` badge inside the row's openable text area, so the indicator sits within the row's selection highlight; its tooltip names the affected fields, clicking it applies the `manual` filter, and the toolbar's `metadata` filter (a combo box offering `auto or manual` and `manual`) sets the same filter, which participates in paging, bulk selection, and streamed deltas like the other dimensions. The manual override count beside the metadata filter reports the session's `manual_overrides_total`, and the metadata editor labels each overridden input as manual. The header carries only the app title, the session state badge, the scan root, and the scan/config/theme actions, because counts belong beside the controls they describe rather than in one crowded row: the batch's suggestion total and the filtered match count (`42 of 1234 suggestions`, or `1234 suggestions` while no dimension is constrained, from `suggestionCountLabel`) follow the filter row's `reset` button, the `N selected` count sits beside `select filtered` and `clear filtered`, and the `N manual` count sits beside the metadata filter whose `manual` value selects exactly those suggestions. The header is one flex row that wraps onto additional lines when the whole row cannot fit, so no item is ever cropped, and the scan-root label is capped at 30vw and truncates from the left (an rtl line box wrapping an inner ltr span, so the path is never bidi-scrambled and its deepest segments stay visible), keeping the scan, config, and theme actions at the right edge fully visible; the filter row and the bulk-action row each wrap internally, so a narrow window stacks the controls instead of cropping them. Two actions in the pane change a move's destination without a scan: the metadata tab's `save metadata` and `fetch metadata` buttons sit together under the editor, and the preview tab renders `rebuild` as an icon button (a circular-arrow glyph) directly after the destination path's copy button, so it reads as an action on that path. Saving applies the entered values and returns the rebuilt row in one call; fetching calls `POST /suggestions/{id}/refresh`, is disabled while the suggestion is pending, and surfaces a failed request as a toast, so a stale or unwanted provider result is discarded and re-fetched; the row is rebuilt again automatically when the fresh provider result lands, so neither action needs a separate rebuild step. When the suggestion has manual overrides, the fetch button first opens an in-page confirm modal naming the fields (the same `modal-backdrop`/`modal` pattern as the other destructive confirmations, with cancel focused); confirming calls the refresh endpoint with `clear_overrides=true`, clears those overrides, and re-requests the provider values, while canceling leaves them in place. The fetch button is offered only on the metadata tab, and `rebuild` only in the preview, so the metadata tab carries the two metadata-producing actions and the preview carries the destination-only action. An `x` icon button dismisses the pane. The scan dialog is the single place to configure a scan, since it determines the next scan's settings, and it edits the service's persistent configuration directly: it offers individual controls for the scan root, the hidden-file toggle, and one target-path override input per asset kind (empty clears the override and uses the built-in default); in the macOS desktop shell the scan-root field also carries a `browse...` button that opens the native directory chooser through Tauri IPC and fills in the chosen absolute path, while a plain browser omits it because a browser directory picker does not expose the absolute path the service needs - all ordinary settings saved through the same settings path - plus collapsible sections for scan exclusion globs, geocoder and description provider transport (service, endpoint, model, API key, language, contact, neighbourhood cities, rate limit), the duplication threshold, limits, the cache, and per-format document-extraction commands. Every configuration-backed control starts at the effective configuration's value, and the collapsible sections' changes are persisted to the service as they are made: edits are debounced, computed as a minimal partial document (cleared optional values are sent as `null`, which deletes the key and restores the built-in default), and written through `PUT /config`, so the service's merge, validation, atomic file write, and `config.updated` broadcast remain the single path for durable changes and the SPA and service stay in lock step. The scan root, hidden-file toggle, and target-path overrides are persisted the same way, but only when the scan starts. The scan request itself therefore carries no `config` overlay; a scan always runs under the configuration that was just saved, snapshotted when the scan is accepted. Failed saves are surfaced inline and retried on the next edit; starting a scan first flushes any pending edit and does not start while a save is failing. When the configuration changes in another client, the form re-seeds every field the user has not touched from the fresh document; touched fields keep their values until their pending save lands, so concurrent edits are never clobbered. API key inputs are write-only (the service never returns them): typing a key persists it to the configuration like any other field, the input clears once stored, an empty field leaves the stored key untouched, and removing a key is done in the config file. Readiness warnings from the service (the `warnings` object in the config document; see "Schema rules > Validation split") are listed inline under the form when an enabled provider is missing a required value or carries a key its service ignores, so a mid-edit incomplete provider setup guides the user rather than failing the save. The configuration view is a pure live mirror of the service's effective configuration, with no reload or edit actions: it renders the `GET /config` document (plus the config file path and per-kind built-in destination defaults) and refetches it whenever the session's `config_hash` changes, whether announced by the `config.updated` event or noticed by the 2-second poll, so what it shows always matches the service no matter which client changed the configuration. The SPA compares `batch_config_hash` against `config_hash` to warn when the displayed batch is stale; saved changes apply to the next scan (the running scan keeps its snapshot). The view's actions are opening the metadata cache viewer and closing. That viewer is a modal (not an inline panel) opened by the toolbar's `view cache` button and dismissed by its `x` close button, a click on the backdrop outside it, or Escape, like every SPA dialog: the shared stack in `webui/src/lib/modal.ts` turns Escape into a dismiss that calls the same close callback as the close button and closes only the topmost open dialog, so the clear-cache confirmation stacked over the viewer closes first and a second Escape closes the viewer, the configuration screen registers itself as the bottom of that stack (Escape closes it like its close button), while with no dialog open Escape keeps its other meanings (clearing the focused path filter); it lists `GET /cache` entries newest first (created, kind, provider, value, and a shortened input hash) with a kind filter seeded from `kind_counts`, a refresh button, and a `caution`-styled `clear cache` button after the refresh button, so the user can inspect what repeated scans would reuse and clear it from the same place. Because clearing is destructive (all cached provider results are lost and the next scan re-extracts from scratch), it is not wired directly to `DELETE /cache` but opens an in-page confirm modal (the same `modal-backdrop`/`modal` dialog pattern used for the stale-configuration warning, not a browser-native dialog) whose destructive action uses the same filled red `caution` style as `execute` and where cancel, not confirm, receives the initial focus; Transient notices render as toasts fixed at the bottom right, each dismissed by its own `x` button or automatically about 4.5 seconds after its last notice: notices are identified by a stable key and a repeat merges into the visible toast, restarting its clock, so a burst of identical notices refreshes one toast instead of covering the screen, and at most four toasts are visible at once with the oldest dropped first. Counted notices aggregate their total in the merged label, so the per-suggestion `batch.validated` rejections read as one `re-validation rejected N suggestion(s)` toast rather than one toast per rejected suggestion. after a clear, an open viewer reloads. The built app (`webui/dist`) is served by the `web` command from the same process that serves the API (Option A distribution: no separate frontend server). During development, `vite dev` proxies `/api/v1` to a running `homelinter web` instance (see "Developer Environment").

The run view carries no console log and no spinner: it is one status list over the complete set of requested suggestions, live from first operation to final report. When a run starts, the SPA builds one row per requested suggestion in the service's execution order (moves first, then deletes, each by source path, mirroring the documented order under "Transactional Safety"), fetching by id, in modest chunks, any requested suggestion outside the loaded browse window so every row is present from the start; each row renders a past-tense action sentence (`moved <path> to <path>`, `deleted <path>, duplicate of <path>`) - never a suggestion id - because the list reports what happened, while the browser's proposal rows keep the imperative `move`/`delete` - with a fixed-width status word on the left (`pending`, `running`, `done`, `partial`, `failed`, `skipped`; the API's internal `executed` result is displayed as `done`), colorized by outcome, and rows outside the scan root fall back to their absolute form under the same truncation rule. `actionLabelParts` builds that sentence as display parts, so the run list sets only its path segments in the monospace stack (the same machine-readable-content rule as the detail preview) while the connecting words stay in the sans-serif UI typeface. The list uses the same `@tanstack/react-virtual` windowing as the suggestion browser, and it auto-follows the active row like a console unless the user scrolls away (scrolling back to the bottom resumes following). The run view is a modal over the suggestion browser rather than a replacement page: it renders in the shared `modal-backdrop` (inset 16px, like the full-screen preview) as a `.run-modal` panel that fills the remaining window area, the status list scrolling inside it, with the browser's rows still mounted underneath, dimmed and covered along with the app header until the view closes. Its header carries, top right, an `x` close icon button (`aria-label="close execution view"`) pushed past the header's left-flowing content and sitting above the status list's download icon; a click on the backdrop outside the panel and Escape (through the shared dismissal stack, so a dialog opened above it closes first) run that same exit. Closing works during the run too - leaving mid-run lets the run continue in the background (toast: `execution continues in the background`), and the run's `execution.complete` event then refreshes the suggestion rows instead of yanking the view back, which is also how a run finished by another client is observed while the SPA is elsewhere - so the view is re-entered only by starting another run. Beside it sit the session state label, one progress meter over the suggestions that have reached a final result (the scanning view's track, `done/total` beside it), and cancel, with the summary counts immediately after the disabled cancel button once the final report is in; the header's content flows from the left, only the close icon is pushed to the right edge, and the download icon button floats at the top-right corner of the status list itself. The summary is inline text rather than a paragraph, so it stays vertically centred on the same line as the state, progress count, and cancel button. `execution.op` events fold into the rows in O(1) via an id-to-index map built once plus a monotonic active-row pointer: because the service executes one suggestion at a time and publishes a suggestion's operations only after the whole suggestion has finished, an operation arriving for a suggestion past the active one finalizes the earlier rows from their own operations, deriving each result the way the service's report does (no operations skipped, a failed parent failed, a completed parent with a failed dependent repair or a detail-carrying move partial - the published cross-filesystem completion) until the final report confirms or corrects them; the report merge also marks requested ids without a report entry `skipped` (already executed, rejected at validation, or skipped by cancellation with no operations) and parks the active pointer, so the meter always reads 100% at the end. The summary counts read the same words as the TUI report through `countsSummary` (`done=n  partial=n ...`, zero halves omitted, `no actions done` when nothing ran), with successful actions counted as `done`, and each count is coloured by its outcome's goodness - the colours its rows use on the list (`done` in the ok green, `partial` in the busy amber, `failed` in the bad red; `skipped` and the empty summary keep the dim grey) - via `countsSummaryParts`; there is no summary pane below the list, so the status list and header are the whole run view. A partial run keeps a plain warning line below the list - some operations completed without finishing source cleanup or dependent repairs - and a run error shows as a plain error line there too. The download icon button (a downward arrow into a tray, `aria-label="download report"`) floats over the top-right corner of the status list rather than taking a place in the header: activating it opens a save dialog so the file's location is chosen explicitly where the browser supports the File System Access API (`showSaveFilePicker`, which the Chromium launcher provides on the localhost origin), and falls back to a plain anchor download elsewhere (Firefox and embedded WebViews), which uses the browser's own download location; cancelling the save dialog writes nothing and raises no notice. The downloaded document is plain ASCII text built client-side by `executionReportText` in `webui/src/lib/report.ts` from the final report plus the run model (so requested suggestions the report omits as skipped still appear), ordered by importance: the title and summary counts first, then a recorded run error, the scan root, platform, the `scanned` and `executed` timestamps, the `generated` timestamp and the partial flag - the three timestamps printed in one uniform form, UTC at second precision in ISO 8601 (`2025-03-05T14:02:11Z`), whether the source value carried fractional seconds, a non-UTC offset, or was the local generation clock - then the errors - every failed or partial action with its failed, skipped, or detail-carrying operation outcomes, dependent symlink repairs included - and finally every action in execution order, each with its notable per-operation outcomes and the full absolute paths the report recorded. Successful action statuses read `[done]`, and action and operation verbs are past tense (`moved`, `deleted`, `repaired symlink`). A plain completed parent operation is not repeated under its action line, and a skipped action with no operations says so. The file is named `homelinter-execution-report-<UTC timestamp>.txt`.

### macOS Desktop Application

The desktop shell is a Tauri 2 application in `crates/desktop/src-tauri` (crate `homelinter-desktop`).
It is an additional client packaging, not a fourth implementation of the service: it links `homelinter-service` in-process, binds an ephemeral loopback listener, waits up to ten seconds for `GET /api/v1/health`, and points its WebView at `http://127.0.0.1:<port>/`.
The backend is therefore a thread inside the app process rather than a child process, so closing the app cannot leave an orphaned service behind.
The built SPA is shipped as the Tauri resource `webui` (`Contents/Resources/webui` in the packaged app); the shell resolves it through Tauri's resource directory and falls back to the workspace's `webui/dist` during development, with `HOMELINTER_WEB_DIR` as an explicit override.
The service serves both the SPA and the API from that one origin, so the SPA's relative `/api/v1` URLs, SSE connection, previews, and Content Security Policy keep working unchanged.

Native shell integration is deliberately narrow: the only extra command the SPA may call is the dialog plugin's `open` command, used by the scan form's `browse...` button to pick the scan root. `capabilities/default.json` grants that permission to window `main` only, and only for remote content from `http://127.0.0.1:*`, the service's loopback origin, with `local: false`; the rest of the SPA keeps talking to the service over HTTP and uses no other Tauri permissions. The shell registers `tauri-plugin-dialog`, and the SPA detects its injected IPC intrinsics, so a browser deployment never renders the button.

The window is an ordinary resizable macOS window with a title bar, but no browser chrome.
There is no location bar, bookmark bar, back/forward buttons, tab strip, or extension UI, because the content is a Tauri WebView window rather than an embedded browser.
The user can resize, minimize, or quit the window normally.

The shell owns the service's shutdown watch.
`Built` exposes its `shutdown_tx`; on Tauri's `RunEvent::Exit` the shell sets the watch, waits up to five seconds for the HTTP task to finish, and then the process exit closes the listener regardless.
This mirrors the CLI/TUI invariant that an invocation-owned service never outlives its client, without an HTTP shutdown call or child-process supervision.

### Linux AppImage Launcher

The Linux deliverable is an AppImage driven by `crates/launcher` (crate `homelinter-app`), a launcher with no GUI toolkit rather than a Tauri build.
It links `homelinter-service` in-process, binds an ephemeral loopback listener, waits up to ten seconds for `GET /api/v1/health`, opens `http://127.0.0.1:<port>/` in an app-mode window of a browser the user already has, and shuts the service down when that window closes.
A browser-hosted shell is the deliberate Linux choice: bundling WebKitGTK pulls in GTK, GStreamer, GIO modules, and fontconfig, which is what usually breaks AppImages on NixOS and other non-FHS systems, while the launcher links only glibc and libgcc.
App mode is requested from the Chromium family (`chromium`, `google-chrome`, `brave`, `microsoft-edge`, `vivaldi`) with `--app=<url>`, producing a window with no location bar, bookmark bar, back/forward buttons, or tab strip; Firefox has no app mode and is started with `--kiosk` as the chrome-less fallback.
`HOMELINTER_BROWSER` accepts a program plus arguments (for example `flatpak run org.chromium.Chromium`) and wins over detection.
The launcher keeps one reserved browser profile, `$XDG_DATA_HOME/homelinter/browser` (next to the service's data directory, `HOMELINTER_BROWSER_DATA_DIR` overrides it), rather than the user's own profile or a throwaway directory: the user's profile would mix the app's cookies, history, and extensions into their real browsing, and a fresh directory per run would discard the state the browser keeps for the app on every launch.
One profile is shared by every invocation, so a non-blocking `flock` on `<profile>.lock` admits one launcher at a time and a second start fails with a message instead of taking over the window that is already open (Chromium would otherwise hand the URL to the running instance and exit, stopping the new service under the old window).
The kernel drops the lock with the process, so a killed launcher never blocks the next start, and the profile sits under a hidden directory that the default hidden-file setting keeps out of a scan.
The browser is spawned in its own process group, so Ctrl-C or SIGTERM forwards `SIGTERM` to the whole browser tree before the service stops, and a browser still alive after three seconds is killed.
A launcher that dies without running that path, through `SIGKILL` or because its supervisor was killed, leaves the browser unreaped as an orphan window pointed at a stopped service; the documented quit paths are the window close, Ctrl-C, and SIGTERM.
SIGHUP is caught and drained for the launcher's lifetime, so a launch detached from its terminal with `setsid ... &` keeps both the in-process service and the browser window alive; closing the window, Ctrl-C, and SIGTERM are still the only quit paths.
A supervisor wrapper that dies on SIGHUP still takes the invocation down, and NixOS is such a system: `binfmt` registers `appimage-run` for both AppImage types, and its bubblewrap supervisor (which uses `--die-with-parent`) does not ignore SIGHUP, so the sandbox, the launcher, and the service exit with the terminal.
`nohup ... &` does not fix that, because `nohup` only sets `SIG_IGN` in the process it starts while an interactive shell resends SIGHUP to the entire job process group on hangup, the supervisor included.
The launch must escape the shell's session instead: `setsid ... &` starts the AppImage in a new session with no controlling terminal, so no hangup is ever delivered, and the launcher's own handler keeps it alive after that.
The bundled SPA lives at `usr/share/homelinter/webui` and is resolved relative to the executable, with `HOMELINTER_WEB_DIR` still taking precedence.

## Distribution & Packaging

### macOS

The macOS deliverable is a universal `.app` inside a `.dmg`, in either an unsigned or a signed and notarized form.
The unsigned form is the default and requires no Apple account: macOS blocks the first launch of a downloaded copy until the recipient approves that app once, without disabling Gatekeeper globally.
The signed form requires an Apple Developer Program membership, a `Developer ID Application` certificate, and Apple's notarization service; it opens without a Gatekeeper warning.
A physical Mac is not required: `.github/workflows/macos-release.yml` runs the build on a GitHub-hosted `macos-14` runner, which is Apple hardware.
The workflow runs the Tauri CLI, whose `beforeBuildCommand` builds the SPA with pnpm; the CLI then builds `crates/desktop`.
When all six Apple secrets are present the CLI also signs, notarizes, and staples the app; when none are present it skips signing and produces an unsigned DMG; a partial set fails the workflow before building.
The workflow publishes `INSTALL-macOS.txt` alongside the DMG with the approval steps for unsigned builds or the normal launch steps for signed builds.
The step-by-step no-Mac checklist, including the unsigned approval steps and the optional certificate setup on Linux, is in `docs/macos-release.md`.

Tauri and its build-time crates are pinned (`tauri` 2.11.1, `tauri-build` 2.6.3, `tauri-utils` 2.9.3) because Tauri 2.12 and newer transitive releases raised their MSRV above the workspace's Rust 1.85 toolchain; `tauri-plugin-dialog` is pinned to 2.7.3 for the same reason, since 2.8 requires Rust 1.90.
The Tauri CLI is invoked through `pnpm dlx @tauri-apps/cli@2.11.1`, so the release builder does not recompile the CLI under the older toolchain.
The desktop crate is its own Cargo workspace, excluded from the root workspace (`exclude = ["crates/desktop/src-tauri"]`).
It declares `rust-version = "1.85"` and `resolver = "3"` and commits its own `Cargo.lock`, so MSRV-aware resolution does not select newer transitive crates; the exclusion also means `cargo test --workspace` on Linux never needs WebKitGTK or other Tauri system libraries.
The shell is built explicitly on macOS with the Tauri CLI.

### Linux

The Linux deliverable is a single x86_64 AppImage named `homelinter-<version>-x86_64.AppImage`, assembled by `packaging/appimage/build.sh` and published by `.github/workflows/linux-release.yml` on `v*` tags.
The script builds `homelinter-app` itself (unless `BIN` names an explicit binary) before laying out the AppDir, because packaging a `target/release` binary left over from an earlier build silently ships an old service with the current SPA. The workflow builds the SPA with pnpm, builds `homelinter-app` with Rust 1.85.0, lays out an AppDir (launcher, `usr/share/homelinter/webui`, desktop entry, 512x512 icon, and AppStream metadata), and runs `appimagetool` 1.9.1 (checksum-pinned) with `APPIMAGE_EXTRACT_AND_RUN=1`, so the runner needs no FUSE.
Builds run on `ubuntu-22.04`, giving a glibc floor of 2.35 (Ubuntu 22.04+, Debian 12+, Fedora 36+).
A smoke test runs the finished AppImage with `HOMELINTER_BROWSER=true`, exercising the bundled SPA lookup, the in-process service, the health check, and the shutdown path without a display.
The workflow publishes `INSTALL-Linux.txt` with the browser requirement, the FUSE fallback, and the NixOS instructions (`programs.appimage.enable` with `binfmt`, or `appimage-run`), and `docs/linux-release.md` carries the full guide.
The AppImage is the only packaged Linux artifact: a deb or rpm would declare `libwebkit2gtk-4.1-0` and `libgtk-3-0` that neither the AppImage nor NixOS needs, and Flatpak or Snap confinement would require broad home-directory access to do the job at all.
A native Nix package (flake `packages.homelinter` and `packages.homelinter-desktop`) and an aarch64 AppImage are not implemented yet.

Optional signing secrets for the signed route:

| Secret | Meaning |
|--------|---------|
| `APPLE_CERTIFICATE` | base64-encoded `Developer ID Application` `.p12` certificate |
| `APPLE_CERTIFICATE_PASSWORD` | password for that `.p12` |
| `APPLE_SIGNING_IDENTITY` | certificate identity, for example `Developer ID Application: Name (TEAMID)` |
| `APPLE_ID` | Apple ID that owns the team |
| `APPLE_PASSWORD` | app-specific password for that Apple ID |
| `APPLE_TEAM_ID` | Apple Developer team identifier |

The signed route uses the hardened runtime but not App Sandbox; the unsigned route has no signature, so there is no hardened runtime to set.
Notarization does not require sandboxing, and homelinter must scan the user's home directory and move files to destinations the user chooses; the App Store sandbox model would require broad user-selected-folder entitlements and change the product's behavior.
`Info.plist` supplies the macOS privacy purpose strings for Desktop, Documents, Downloads, removable volumes, and network volumes, so the normal folder-access prompts explain why the app wants access.
The app is distributed outside the Mac App Store; the signed route avoids Gatekeeper prompts, while the unsigned route documents the one-time per-app approval and never asks the user to disable Gatekeeper system-wide.

Release build command (on macOS; the Tauri CLI's `beforeBuildCommand` installs the SPA dependencies and rebuilds `webui/dist` first):

```
cd crates/desktop
pnpm dlx @tauri-apps/cli@2.11.1 build --target universal-apple-darwin
```

Without the six Apple secrets this command produces an unsigned app; with them it signs and notarizes the app.

The resulting disk image is under `crates/desktop/src-tauri/target/universal-apple-darwin/release/bundle/dmg/`.
For development on a Mac, `pnpm dlx @tauri-apps/cli@2.11.1 dev` from `crates/desktop` rebuilds the SPA and the shell and loads it from the workspace; it does not require signing.

## Command-Line Interface Schema

The CLI has plain scan and non-interactive modes (see "User Interfaces"). The supported command-line syntax is:

```text
homelinter [OPTIONS]
homelinter web [OPTIONS]
homelinter tui [OPTIONS]
```

Supported options:

| Option | Value | Meaning |
|---|---|---|
| `--config` | `<path>` | Select the configuration file. |
| `--root` | `<path>` | Seed the scan root setting for this invocation. Relative paths are resolved against the current working directory; the resolved path is converted to an absolute path before scanning. Persisted to the configuration when written through the settings API; defaults to the platform's home directory. |
| `--execute` | none | Execute all generated top-level suggestions and their dependent operations immediately, without review. |
| `--export` | `<path>` | Scan and generate suggestions, write the complete executable shell plan, including dependent symlink repairs, to `<path>`, and exit without executing it. |
| `--hidden` | none | Include hidden files and directories in primary discovery. |
| `--format` | `<pretty\|json\|toml>` | Override `output.format` for this invocation. |
| `--target-path` | `<kind>=<path>` | Seed the destination format string setting for one Asset Kind for this invocation. Repeatable; each Asset Kind may be supplied at most once. Takes precedence over `target_paths`. |
| `--cache-clear` | none | Clear the persistent metadata cache before this invocation performs any scan or execution. May be combined with any other mode; alone it runs the default plain scan flow. |
| `--theme` | `<dark\|light>` | Seed the SPA color theme for this invocation; accepted by `web` only. The SPA toggle persists later changes through `PUT /config`. |
| `-v`, `--verbose` | none, repeatable | Increase structured logging verbosity. |
| `-q`, `--quiet` | none, repeatable | Decrease structured logging verbosity. |

`--hidden` applies only to primary discovery and does not affect the separate home-wide symlink repair pass (see "Symlink Handling"). Like `--root`, it seeds the `scan.hidden` runtime setting at launch and is then editable through the settings API. What counts as hidden is platform-native and on Windows configurable via `scan.hidden_definition` (see "File Classification").

`--execute`, `--export` are mutually exclusive. Each is also mutually exclusive with the default plain scan flow. `--config`, `--root`, and `--export` may each be supplied at most once. `--cache-clear` is orthogonal: it may accompany any mode, including the plain scan flow, and never implies scanning beyond the selected mode. If both `--format` and `output.format` are supplied, `--format` takes precedence. `--target-path` takes precedence over `target_paths` for the kinds it names; supplying the same kind twice is an error, as is an unknown Asset Kind or an invalid format string. Conflicting verbosity options are an error. `--export` takes an output path and fails if the path cannot be created or safely written.

The `web` subcommand launches the standalone service described in "User Interfaces". It accepts common configuration and scan options, including `--config`, `--root`, `--hidden`, `--target-path`, `--cache-clear`, `--theme`, and logging options, but not `--execute` or `--export`; execution is initiated through the SPA. `--port <n>` pins the loopback listener to a fixed port instead of an ephemeral one, so a development SPA proxy (default `HOMELINTER_WEB_PORT` 8787) can target a stable address; an ephemeral port remains the default. `--root`, `--hidden`, `--target-path`, and `--theme` seed the service's initial effective settings; the SPA reads them from `GET /config` (and its theme from `GET /session`), and every later edit is persisted through `PUT /config`. With no `scan.root` set, the platform home directory applies.

The `tui` subcommand starts the full-screen terminal interface described in "User Interfaces > TUI". Like `web` it accepts `--config`, `--root`, `--hidden`, `--target-path`, `--cache-clear`, and the logging options, but none of `--execute` or `--export`; those actions are available inside the TUI. `--root`, `--hidden`, and `--target-path` seed the service's initial effective settings, which the TUI loads from `GET /config`; the `n` settings form saves changed values through `PUT /config` immediately before starting the next scan.

**Plain scan (no `--execute`)**, default:
1. Scan the selected root and generate suggestions.
2. If no suggestions were generated, print a "no suggestions" notice and exit.
3. Print how many suggestions were generated and point the user at the review and action entry points: `homelinter tui` for full-screen review, `--execute` to apply everything, or `--export <path>` to write an executable plan script. Nothing is executed or exported in this mode.
4. Exit without acting.

Plain scan requires a terminal: when stdin is not a terminal it refuses to run and directs the caller to `--execute` or `--export`, so scripts never get a silent no-op scan.

**Non-interactive mode (`--execute`)**
- Acts without review: no summary pointer is shown.
- Scans, generates suggestions, and executes them immediately.
- Every executed operation is recorded in the audit log; live per-operation events are available over SSE (`execution.op`). The CLI prints the final report: in pretty mode on stdout, and in json/toml modes stdout carries only the final document while progress and notices go to stderr (see "Output & Reporting > Machine-Readable Output").
- `Ctrl+C` terminates the process; already-completed operations are not rolled back.

## Service API

The service exposes a single HTTP API on a localhost-only listener. The CLI and TUI spawn an ephemeral instance and drive it through this API for the duration of the client session. The `web` command serves the SPA from the same process and exposes the identical API to the browser. The CLI, TUI, and SPA are therefore interchangeable clients of one backend contract.

### Transport & Conventions

- **Base URL**: `http://127.0.0.1:<port>/api/v1`. The port is ephemeral. Every path in the endpoint tables below is relative to this base: `GET /health` is served at `GET /api/v1/health`, `POST /execute` at `POST /api/v1/execute`, and so on. The managed CLI embeds its service in-process and polls `/health` until it returns 200; the standalone `web` command prints the readiness line `homelinter: listening on 127.0.0.1:<port>` to stdout for external clients, which parse it and then poll `/health`. The SPA uses the same origin it was served from.
- **Protocol**: HTTP/1.1 REST with JSON request and response bodies (`Content-Type: application/json`), plus one Server-Sent Events stream for push updates. The server is unauthenticated, binds loopback addresses only, and rejects non-loopback Host headers.
- **Paths**: every path in a request or response is an absolute, normalized, host-native path per "Scan Root and Path Representation". The service rejects relative paths, `~`, and environment-variable references in request inputs with a 422 error. The CLI resolves `--root` and `--export` paths to absolute form before calling the API.
- **Errors**: errors are returned as `{"error":{"code":"<machine-code>","message":"<human text>","details":{...}}}` with a status of 400 (bad request), 404 (not found), 409 (conflict with the current session state), or 422 (validation failure).
- **Idempotency**: suggestion IDs are stable within a session and derived from the normalized absolute target path, so re-selecting or re-executing a suggestion is a no-op rather than an error. The service retains the report most recently produced by an execution; a re-run of the same batch returns that stored report when it still corresponds to the executed batch, and is rejected with 409 when the stored report covers a different batch, so idempotency never serves a stale result under a different batch's identity.
- **Concurrency**: one scan and one execution at a time per session. A request that conflicts with the current state, for example starting a scan while an execution is running, returns 409.

### Session Model

A service instance holds exactly one in-memory session. The session state machine is:

| State | Meaning |
|---|---|
| `idle` | No scan has been started. |
| `scanning` | File discovery is in progress. |
| `analyzing` | Metadata extraction and suggestion generation are in progress. |
| `ready` | Suggestions are generated and the batch has been validated. |
| `executing` | An execution is in progress. |
| `done` | Execution finished; the report is available until the next scan. |
| `failed` | A scan or execution failed, or a scan was cancelled; no suggestions or a partial report is available, resolved by a new scan. |

A scan that produces no suggestions reaches `ready` with an empty batch: suggestion counts are zero, and clients present a "no suggestions" notice. The empty batch is a valid validated batch; execution on it is rejected with 400 by the existing empty-selection rule.

State transitions: a new scan replaces the session from `idle`, `ready`, `done`, and `failed`; starting one from `scanning`, `analyzing`, or `executing` conflicts with the in-progress operation and returns 409 (cancel first). A new execution is accepted from `ready` and `done`. And only `ready` is never re-entered from a later state except by a new scan. A scan or execution that fails at any point transitions to `failed`, and the failure's reason and any partial report are retrievable until the next scan replaces them.

**Cancellation**: a `POST /cancel` cooperatively cancels the in-progress scan or execution. A scan stops promptly and transitions to `failed` with a cancellation reason: the discovery walk (primary and home-wide symlink pass) and the analysis loop poll the cancellation flag continuously (per entry and per file), so a cancel lands mid-phase instead of waiting for the whole tree or the full extraction batch to finish; the partial result is discarded and the session reports `failed` with a cancellation reason. An execution finishes the top-level suggestion it is working on, marks the remaining ones `skipped` with a cancellation reason, and transitions to `done` with the partial report. Already-completed operations are never rolled back. Cancelling an idle session is a no-op returning the current state. In `ready`, `done`, or `failed` state nothing is in progress, and cancellation returns 409. A later execution naming only the skipped-from-cancellation suggestions (a different batch identity) executes them fresh, while re-running the full batch returns the stored partial report.

A restart requires a new scan: session state (suggestions, selection, progress, report) is never persisted. Runtime settings, by contrast, persist in the configuration file. The scan root is captured when the scan starts and is retained with the session (see "Scan Root and Path Representation").

**Guarded actions**: the service rejects requests that contradict the state machine with 409 (a new scan during `scanning`/`analyzing`/`executing`, execute/export outside `ready`/`done`, cancel when nothing is in progress). Clients mirror these guards so the controls are disabled before the user attempts them: the SPA derives disabled states from `GET /session` (scan/start disabled while a scan or execution is in progress, execute/export disabled unless the session is `ready` or `done`, cancel disabled otherwise) and the TUI only dispatches the matching keys in the phase where the action is legal (see "User Interfaces").

**Configuration snapshot per scan**: the service snapshots the effective configuration at the moment a scan is accepted. Every phase of that scan (discovery, analysis, suggestion generation, provider planning) runs against that one snapshot, so a config save during a scan never changes the running work and the published batch reflects a single committed configuration. Edits saved mid-scan affect only the next scan. The session exposes both the live effective config hash (`config_hash`) and `batch_config_hash`, the hash of the snapshot the current batch was scanned under; clients compare the two to flag a stale batch and offer a re-scan before execute or export (see "Service API > Session & Scan").

### Data Types

**Suggestion**:

```json
{
  "id": "s-<sha256-of-normalized-target>",
  "type": "move",
  "asset_kind": "photo",
  "target": "/home/alice/Downloads/IMG_0001.jpg",
  "new_path": "/home/alice/Pictures/2024/03/IMG_0001.jpg",
  "reason": "",
  "metadata": {"extracted_date": "2024-03-15", "source": "exif"},
  "manual_overrides": ["location", "subject"],
  "dependent_operations": [
    {"type": "repair_symlink", "link_path": "...", "recorded_target": "...", "replacement_target": "..."}
  ],
  "selected": false,
  "status": "pending",
  "rejection_reason": null
}
```

- `type`: `move` or `delete`. `new_path` is present only for `move`.
- `manual_overrides`: for a move, the editable-field subset (`location`, `subject`, `author`) currently backed by saved manual overrides; omitted when empty (deletes never carry it). It is derived from the persisted overrides, so it also survives a restart and a later scan.
- `dependent_operations`: mandatory members of the parent execution unit. They are never independently selectable, rejectable, or executable; the API rejects any request that names one.
- `selected`: client selection state, maintained by the service.
- `status`: `pending`, `rejected`, `executed`, `partial`, `failed`, or `skipped`. `rejected` carries `rejection_reason` from batch validation and is never executable or exportable. `partial` means the parent operation completed but its unit did not fully finish (a failed dependent repair, or a verified cross-filesystem copy whose source could not be removed), and it is never re-executed automatically.

**ExecutionReport**: one entry per top-level suggestion with `suggestion_id`, `result` (`executed`, `partial`, `failed`, `skipped`), per-operation outcomes including dependent `repair_symlink` steps, and `partial` (true when any entry is `partial`). An entry is `partial` when its parent operation completed but the unit did not fully finish: a dependent repair failed, or a verified cross-filesystem copy was published while its source removal failed (the leftovers are named in the move operation's `detail`). A `partial` suggestion is never retried automatically; the report also records the scan root, platform, and, in service-produced reports, the optional `scan_started_at` and `executed_at` RFC 3339 timestamps.

**ScanSummary**: total files scanned in the primary scan, total symlinks indexed for repair, suggestions by type and Asset Kind, and estimated space reclaimed by deduplication.

### Client Lifecycle

The CLI and TUI spawn the service, parse the readiness line, poll `/health` until 200, drive the session through the API, then call `POST /shutdown` and wait for process exit, force-terminating if the process does not exit promptly. An invocation-owned service must not outlive its client. The `web` command serves the SPA at `/` and the API under `/api/v1` from the same process; it never shuts itself down and is terminated explicitly by the user.

The non-interactive CLI modes map directly onto this API: `--execute` scans and executes with all suggestion IDs, and `--export <path>` scans and calls `POST /export` with the resolved path. After a scan reaches `ready`, the CLI waits for the batch's provider metadata requests to finish before listing or acting on suggestions, printing `resolving metadata requests: completed/total` as each suggestion completes; this keeps it from silently skipping suggestions whose destinations were still being resolved (they are never executable while pending). The plain CLI scan reports through the same endpoints and prints its summary from them; the TUI uses the same endpoints and adds live progress over SSE.

## Tooling Strategy

homelinter shells out to external tools for discovery and metadata extraction:

| Task | Primary Tool | Fallback |
|------|-------------|----------|
| File discovery | `fd` | `find` |
| EXIF extraction | `exiftool` | Built-in `kamadak-exif` (Rust) |
| Audio tag/stream extraction | `exiftool` | Built-in `lofty` (Rust) |
| Document metadata extraction | `pdfinfo` (PDF) | Built-in zip/XML reader (Rust, docx/odt/epub) |
| Document text extraction | `pdftotext` (PDF), `pandoc` (docx/odt/epub) | Built-in `pdf-extract` (PDF) and zip/XML readers (docx/odt/epub) |
| Video frame extraction (description vision) | `ffmpeg` (`ffprobe` for the seek point) | Text-only prompt (no frame) |
| SVG rasterization (description vision) | In-process `resvg` | Text-only prompt with extracted SVG text |
| Git info | `git` CLI | - |
| Hashing | Rust `sha2` crate | - |

**Embedded metadata extraction** is implemented as a plug-in chain consulted in fixed priority order per analyzed file, with the first `Some` winning each field; every extractor failure degrades to missing metadata and analysis never fails because of one. `exiftool` is preferred when it is on the PATH and covers photos, videos, and audio with a fixed, small tag list (`-n -json -m`) for date taken (`DateTimeOriginal`/`CreateDate`/`TrackCreateDate`/`MediaCreateDate`, with the timezone-aware QuickTime/`Keys` `CreationDate` as a final fallback consulted only when every primary date tag is absent or unparseable) and its UTC offset (`OffsetTimeOriginal`/`OffsetTimeDigitized`/`OffsetTime`, or the offset embedded in a `CreationDate` fallback when that fallback supplies the date), title (`XPTitle`/`Title`/`ImageDescription`, with XMP `dc:description` and the IPTC caption as cataloging fallbacks), artist (`Artist`, with XMP `dc:creator` and the IPTC by-line as cataloging fallbacks), camera (`Model`/`Make`), signed GPS coordinates, and stream `Bitrate`/`Duration`. The catalog and `CreationDate` fallbacks are strictly additive: each is consulted only when the tags it shadows are absent, blank, or (for the date) unparseable, so a value the primary chain already produced can never change - a file can only gain metadata it lacked. For `CreationDate` the offset travels with the date: it is taken from the fallback value itself only when that value is the one supplying `date_taken`, so the offset never describes a different date. Process startup dominates a single-file invocation, so the applicable files are handed to exiftool in chunks of 128 paths per invocation (the chunks themselves run in parallel) and each returned JSON row is mapped back to its input path by the `SourceFile` key. `-m` makes exiftool ignore minor per-file errors, and a nonzero exit still yields whatever rows exiftool emitted (partial output is parsed rather than discarded), so one odd container does not blank its siblings. A batched invocation is granted the configured `tool_timeout_seconds` plus a per-file allowance for every path beyond the first (so a multi-file invocation is not held to a single-file clock while the overall bound stays finite), and a chunk that still fails (timeout, output overrun, or a truncated payload) is retried at half size down to eight paths, so a transient stall or one unreadable file cannot discard metadata for a whole 128-file chunk. Built-in in-process readers follow: `kamadak-exif` for photo containers (JPEG, TIFF, PNG, WebP, HEIF) reads a bounded prefix of each image and reports EXIF, date, its UTC offset, and GPS fields from `In::PRIMARY` (the crate expands the Exif and GPS sub-IFDs under their parent's IFD number, so GPS is recovered even when exiftool is unavailable), and `lofty` for audio/video container tags (ID3v1/v2, FLAC, Vorbis Comments, MP4/M4A, WAV, AIFF) reads tags structurally by header offsets rather than scanning whole files and also reports stream bitrate and duration. Document metadata is extracted by `pdfinfo` for PDFs (title, author, page count, and the raw creation date via `-rawdates`, falling back to plain output on poppler builds without the flag) and by a built-in reader for OOXML/ODF/EPUB containers (`docx` `docProps/core.xml`, `odt` `meta.xml`, `epub` `container.xml` to the OPF file), which surface `dc:title`, `dc:creator`, and `dc:date` from the container XML; only PDFs supply a page count. The extractor trait returns one `EmbeddedMeta` value per file (date taken, its capture UTC offset when present, title, author, camera, signed latitude/longitude, plus informational bitrate, duration, and page count that no placeholder currently consumes) instead of one method per field, and offers each extractor the whole file set at once: the default batch method runs the per-file extraction in parallel, and exiftool overrides it with the chunked batching above. Because the extractor order is fixed, merging each extractor's batch per field (first `Some` wins) is equivalent to the former sequential per-file merge. Each extractor declares the field set it can fill per Asset Kind (`FieldSet`: date, UTC offset, title, author, camera, latitude/longitude, bitrate, duration, page count), and the analysis hands a pass only the files that still have something to answer for: an extractor marks the fields it examined as settled when it successfully read the container (`EmbeddedMeta::settled`), whether or not the tags were present, and a value it returns settles its own field. A pass is skipped entirely for a file once the merged result answers every field that extractor can fill, and a pass left with no files runs no extraction and reports no progress. That is what keeps the fallbacks from doubling the read cost in the normal case: because exiftool's tag list is a superset of what the built-in `kamadak-exif` reader looks for (it also requests IFD0 `ModifyDate`, the built-in reader's EXIF `DateTime` fallback; the unqualified `-DateTime` is never requested because exiftool resolves it to the file's modification time), a clean exiftool row settles every photo field, so the built-in reader only reads photos exiftool could not handle. A row carrying an `Error` for its own file, a chunk that failed and produced no rows, a missing tool, or a container that failed to parse leaves the file unsettled, so the next extractor still gets its turn. Audio and video dates stay unsettled on purpose: ID3 `TDRC`, Vorbis `DATE`, and container `CreationTime` are not in the tag list, and the `lofty` reader answers them from a structural read that costs no file scan. An extractor that does not declare its fields defaults to `FieldSet::ALL` and is therefore never skipped. External tools run under the bounded tool timeout and stdout cap from `[limits]` with a minimal sanitized environment; stdout is drained on a dedicated reader thread while the child runs, so a tool that produces more than the OS pipe buffer (a batched `exiftool`) can exit instead of blocking on a full pipe, and exceeding the cap still terminates the child.

**Video frame extraction** for the description provider follows the same philosophy: when `ffmpeg` is on the PATH, a vision job for a video (only on a provider cache miss) has representative frames decoded to a per-call scratch directory under the system temp directory, each downscaled and sent to the model exactly like a photo; `ffprobe` supplies the duration so the frames are sampled about once per second, evenly distributed across the clip and thinned to at most `description.max_video_frames` (falling back to ffmpeg's single `thumbnail` filter when it is absent or reports nothing). Because each frame is one inference, the worker multiplies the configured provider timeout by the number of frames sent. The frames are read back from files rather than piped through stdout, which keeps a frame larger than the OS pipe buffer independent of the shared capture path. A missing tool, a non-zero exit, a timeout, or an unreadable frame degrades to the text-only prompt and analysis continues, so `ffmpeg` is never required. That text-only result is applied but not cached under the vision key, so a later `ffmpeg` install re-runs the description rather than reusing a pixel-free guess.

**SVG rendering** for description vision uses the in-process `resvg` renderer only, avoiding a runtime dependency on an external executable. The SVG source and encoded raster are each capped at 20 MiB; parsing denies filesystem image references (embedded data URLs remain available) and does not expose the source directory. The SVG is rendered to a PNG whose longest side follows `description.max_image_dimension` with a hard 4096 px maximum (including when the configured value is zero). The worker also extracts SVG `<text>`/`<tspan>` content, `<title>`, `<desc>`, `aria-label`, and editor `label` attributes through the bounded in-process XML reader and sends that text with the raster, so exact labels remain available even when raster text is small. Rasterization failure degrades to the text-only request; a vision result with no pixels is not cached, so a later successful render can be retried, and an SVG-specific vision cache marker prevents reuse of entries from the previous raw-SVG payload behavior. The renderer is the only new dependency this path adds: bundling `resvg` grows the release binary by about 4.4 MiB (measured 19.4 MiB without and 24.0 MiB with it, unstripped, thin LTO), and raster memory is bounded by the pixel cap (roughly 4 MiB at the default 1024 px), allocated only on a provider cache miss with an SVG input.

**Document text extraction** follows the same runtime precedence as the metadata chain: the configured `[document_extraction]` command for the format, then the default tool when it is on the PATH, then in-process readers as the final fallback when no tool is available. The in-process readers are `pdf-extract` (a `lopdf`-based crate) for PDF and native zip/XML readers for the office/e-book containers, using the same `zip` + `quick-xml` stack as the metadata reader: docx `word/document.xml` `w:p`/`w:t` runs (with `w:tab`/`w:br` mapped), odt `content.xml` body paragraphs and headings inside `office:text` (including `text:s` space runs), and epub in spine reading order (`META-INF/container.xml` to the OPF package, then each spine item's XHTML with head/nav/script markup stripped and common HTML entities decoded). No third-party office crate is used: `docx-rs` is write-oriented and no maintained equivalent exists for odt/epub, so one uniform container reader covers all three formats. The built-ins mirror the external discipline: extraction whose text would exceed the `[limits]` stdout cap is a failure (not a truncated success), files over 128 MiB are refused rather than read into memory, the PDF reader runs under a panic guard so a malformed document cannot abort the worker, and results are trimmed with blank-line runs collapsed. Because the built-ins are only a fallback, their output quality (pdf-extract has no layout preservation, the office readers cover body text only) never displaces a configured tool.

**Repository adapters**: repository metadata (remote URLs, default branch, commit count, last activity) is collected by a pluggable per-VCS adapter following the same pattern as the provider plugins in "Provider Plugins". Adapters for `git` (`.git` directory or file), `hg` (`.hg`), and `svn` (`.svn`) map to their platform CLIs (`git`, `hg`, `svn`). The git adapter uses `remote get-url origin`, `symbolic-ref --short HEAD`, `rev-list --count HEAD`, and `log -1 --format=%ct`; the hg adapter uses `paths default`, `branch`, and the tip changeset's rev and `{date|hgdate}` (Mercurial revision numbers are dense local indexes, so tip rev plus one is the changeset count); the svn adapter parses `info --xml` for the working-copy URL and last-changed date, derives the branch name from the URL path when the layout is standard (`trunk`, `branches/<name>`), and leaves commit count empty because svn revisions are repository-global and counting log entries would require a full repository walk. All adapter commands are local-only (no network round trips) and svn runs non-interactive so credential prompts never hang an unattended scan. An adapter whose CLI is unavailable leaves that repository's metadata empty and analysis continues, exactly like other optional tools; new version-control systems are added behind the same interface without changing analysis code.

External tools are optional and platform-specific. The implementation must use platform-neutral Rust APIs for core discovery, hashing, path handling, and execution safety, with external tools used only when available and compatible with the host platform. Windows equivalents may be used for metadata and repository operations, but missing Unix utilities are never errors when a built-in implementation is available. Tools are detected at runtime. If a primary tool is missing, homelinter falls back gracefully. If no suitable tool is available for a metadata type, that metadata is omitted (analysis continues). Hashing is always in-process via the Rust `sha2` crate: it is a core safety operation used by deduplication and move verification, is required on every platform, and never depends on an external binary.

## Execution & Safety

### Guaranteed invariants

These invariants are non-negotiable and testable:

- homelinter never overwrites an existing object.
- homelinter never modifies file contents.
- homelinter never follows or modifies an unsupported link or reparse point.
- A dependent operation runs only after its parent operation succeeds.
- A stale suggestion whose source identity no longer matches is never executed.
- An invalid or colliding batch is never executed.
- Partial completion and failures are always reported accurately.
- Completed operations are never reported as rolled back.

homelinter does not guarantee transactional behavior across multiple filesystem operations. A later failure may leave earlier operations completed. Cross-filesystem moves and dependent symlink repairs can therefore produce partial completion, and a move that fails after its destination directories were created may leave those empty directories behind; the report does not claim to have cleaned them up.

### Execution policies

Destructive and lower-safety behaviors are gated behind explicit configuration. The proposed defaults favor safety over completeness. Symlink repair and cross-filesystem moves are not configurable:

- Delete suggestions are executable and exportable whenever they pass the same validation and execution checks as other suggestions.
- Suggestions with `metadata_pending = true` (provider metadata still in flight) are never executed, exported, or counted as executable; they become eligible only after their provider requests resolve (see "Provider Plugins > Offline request loop").
- Cross-filesystem moves always use the verified copy-and-delete protocol described under "Transactional Safety"; there is no configuration to weaken or disable it.
- Symlink repair is always performed under the safe-only semantics described in "Symlink Handling".
- Execution always continues with unrelated suggestions after a failure. A failed suggestion and all of its dependent operations are skipped or stopped, while unrelated suggestions remain eligible.
- When an execution completes, every suggestion the report marks `executed` leaves the session's selection (`crates/service/src/pipeline.rs`): the selection count drops with it, clients render the row done (the SPA clears and disables its checkbox), and a later run cannot try to execute it again. Done suggestions are never selectable by any path - explicit ids, a bulk filter (including `select filtered`), or an exact replacement - so a finished action cannot come back as selected. Failed, partial, and skipped suggestions stay selected.

### Transactional Safety

- Suggestions and their dependent operations are validated immediately before execution (re-check destination, re-stat source, and validate dependent symlink state). Execution order is deterministic and dependency-aware: moves run before deletes, and within each group suggestions follow the source sort key. Since a duplicate keeper is itself a move candidate, this guarantees a duplicate delete runs after its keeper's move, never before it.
- Moves use atomic rename within the same filesystem, performed with no-replace semantics so the rename fails rather than overwrites if an object exists at the destination: `renameat2` with `RENAME_NOREPLACE` on Linux, `renamex_np` with `RENAME_EXCL` on macOS, and `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING` on Windows (with `MOVEFILE_WRITE_THROUGH`, and without `MOVEFILE_COPY_ALLOWED`, so a same-volume rename never degrades into an unverified copy). Windows filesystem calls pass absolute paths in the extended `\\?\` form, so paths beyond `MAX_PATH` work like every other std-based operation. The same-filesystem comparison resolves a destination parent that is itself a symlink or junction to its target before comparing volume serials. An existing destination is reported as "destination exists; refusing to overwrite". Where the kernel or filesystem cannot express a no-replace rename, a file is published through a hard link, which fails atomically on an existing target; if hard links are unsupported too, or the object is a directory, the destination is re-checked immediately before a plain rename. That last step is best-effort: a concurrent creation of the same path between the check and the rename can be replaced, so it is used only where the filesystem offers no stronger primitive and only after the executor's own preflight destination check. Linux, macOS, and Windows all take a native no-replace path; the fallback exists for other ports.
- A cross-filesystem move of a file follows a verified copy-and-delete protocol: the copy phase is a buffered read/write loop on every platform (64 KiB buffer), so behavior is identical on Linux, macOS, and Windows and does not depend on optional kernel copy acceleration. The copy preserves file permissions and mtime/atime where the host allows setting them, so an old file does not look newly created after a cross-filesystem move and keeper (oldest copy) selection stays correct. Unlike `mv`, which copies into place without verification, the protocol is: copy to a temporary file in the destination filesystem, `fsync` it, verify it against the source with the full-content SHA-256 hash, publish the copy by renaming the temporary file to its final name within the destination filesystem using the no-replace rename above, and delete the source only after the copy is published. At every interruption point, either the intact source or a complete verified destination exists at its final path; the source is never removed until the verified destination is in place.
The fast-path hash is a deduplication shortlist mechanism only and never verifies a move, so corruption in any part of a large file is detected before the source is removed; the only other thing it decides is whether a drifted mtime is a pure timestamp change, per "Race Condition Handling". A same-filesystem move needs no content pass: it is a single no-replace rename that relocates the object without touching its bytes, and it is preflighted by object identity, size, and - whenever analysis recorded one - the full-content hash (see "Race Condition Handling").
- A duplicate delete re-confirms its duplicate relationship immediately before removal: the recorded keeper (`duplicate_of`) must exist as a regular file, and its full-content hash must equal the delete's recorded provenance hash. That keeper hash is computed at most once per execution batch, since every delete of the same keeper asks the same question about the same bytes. A missing keeper record, a vanished or non-file keeper, or changed keeper content refuses the delete and asks for re-analysis. A keeper that was itself moved - earlier in the same batch, or by an earlier execution of the same session, because the service executes one suggestion per request for cancellation granularity - is followed to its executed destination. The session's stored delete record is republished to that path as soon as the keeper's move executes, which rewrites the `metadata.duplicate_of` value, the human-readable reason, and every dependent repair's replacement target, so a later batch (and `GET /suggestions/{id}`) sees the keeper's current location rather than a stale one. The executor seeds its relocation map from every move in the batch it is handed that has already executed, and adds each move it executes as it goes, so this holds even for a caller that never republished the record. A keeper that is absent or changed at its destination still refuses the delete, so the failure is safe and explicit rather than a lost copy. The delete's dependent symlink repairs point at wherever the keeper exists after execution: the keeper's executed destination when its move ran, and the keeper's original path when it did not, including when the keeper's move failed or was not selected. This holds for both absolute and relative link targets.
- A cross-filesystem move of a directory (a repository root) applies the same verified protocol to the whole tree, and the source tree is untouched until the copy is complete and verified:
  1. Create a uniquely named temporary directory in the destination filesystem.
  2. Copy the tree into it file by file with the verified file protocol above, preserving empty directories and the directory structure, and recreating contained symbolic links from their raw targets without following them; file permissions and timestamps are preserved by the file protocol, while directory timestamps are not preserved. A contained junction or other reparse point cannot be recreated safely and fails the move rather than being dropped, traversed, or copied as a regular file.
  3. `fsync` the copied files and directory entries.
  4. Verify structural completeness: the copy's relative path set must exactly match the source's, and every copied file's full-content hash must match its source.
  5. Publish the copy by renaming the temporary directory to the final destination name with the no-replace rename above; the rename stays within the destination filesystem, and the destination directory is `fsync`ed afterward so the published name is durable before the source is removed.
  6. Delete the source tree only after the publish succeeds.
  A failed or interrupted tree move leaves either the intact source or the complete verified copy at the temporary path, and the temporary directory's path is reported rather than silently removed, because the executor cannot always prove the source is intact afterward. A source-tree deletion that fails after a successful publish is reported as partial completion: the destination remains complete, the move operation's `detail` names the leftover source, and the entry's result and suggestion status are both `partial` (the same applies to a single-file cross-filesystem move).
- A parent move or delete is executed before its dependent symlink repairs. Dependent repairs are mandatory members of the parent execution unit and are executed only if the parent operation completes successfully.
- If a parent operation fails validation or execution, its dependent operations are skipped. Already-completed operations are not rolled back.
- If a parent operation succeeds but one of its dependent symlink repairs fails, the result is reported as partially completed. The executor attempts the remaining safe dependent repairs, while unrelated suggestions remain eligible for execution.

### Suggestion Batch Validation

After suggestion generation, homelinter validates the complete top-level suggestion batch before presenting it in the TUI or SPA. The same validation runs again for every selected subset before export or execution, because interactive selection can change operation dependencies and path conflicts.

Validation uses a deterministic ordering based on normalized absolute source paths and compares paths using the host platform's collision rules, including case folding where applicable (the collision maps are keyed by `path::sort_key`: a Windows build folds case and a Unix build does not). This follows host-platform semantics per "Platform Scope" and does not probe the target filesystem's case sensitivity, so a Unix host scanning a case-insensitive mount (NTFS, exFAT, SMB) will not detect a case-only destination collision during batch validation; the executor's no-overwrite check remains the backstop there. It rejects every suggestion in a collision set when multiple moves have the same destination - no arbitrary survivor is kept - and each rejected member carries a `destination_collision:also=<source sort key of every partner>` reason so clients can show exactly which suggestions conflict. It also rejects any move whose destination conflicts with another planned source (`destination_is_planned_source:also=<sort key>`), a delete target (`destination_is_planned_delete`), or the link path another suggestion's dependent repair rewrites (`destination_is_dependent_operation:also=<sort key>`), unless the plan explicitly defines a safe, order-independent sequence, and rejects any move whose resolved destination has an unsafe final segment (see "Resolution & Sanitization") with an `invalid_destination_segment` reason. A move that carries no destination at all is rejected with a `missing_destination` reason rather than left pending to fail at execution time. Rejected suggestions are reported with a collision reason. Existing destination checks, source identity checks, and symlink precondition checks remain mandatory immediately before execution. Rejected suggestions themselves are never presented as executable, exported, or executed, while the remaining valid suggestions in the batch proceed as planned; the rejected suggestions and machine-readable reasons are included in reporting.

Suggestions whose provider metadata is still in flight (`metadata_pending`) are excluded from batch validation: their destinations are built on fallback metadata, so a collision may disappear once the provider result arrives. They are re-validated against real metadata when their last provider request resolves (see "Provider Plugins > Offline request loop"), and a newly triggered rejection is broadcast as a `batch.validated` event. Validation is monotonic: a suggestion marked rejected is never un-rejected, and re-validation never re-admits a full-batch rejection. Every rejection carries its machine-readable `rejection_reason` on the suggestion itself, so the API, TUI, and SPA can show why each suggestion was rejected.

### Platform Script Export

Export uses the same validated execution plan and dependency order as the native executor. Linux and macOS exports are POSIX shell scripts; Windows exports are PowerShell scripts. The exported language is determined by the host platform at export time and is not configurable, so a Linux or macOS export is always POSIX and a Windows export is always PowerShell. They contain absolute paths, create move destinations, perform moves and deletes, and include dependent symlink repairs only after their parent operation succeeds. Like the executor, a script runs all moves before its deletes, and a duplicate delete's repairs point at the keeper's planned destination when that keeper is moved by the same script, or at the keeper's original path when it is not. Scripts use platform-safe quoting - a path is always a single-quoted shell word and is passed to the script's abort helper as a separate argument rather than interpolated into a message, so a path containing `$`, a backtick, or a double quote can neither run a command nor break parsing - and are not portable between operating systems.

Export re-validates the exact requested subset against a copy of the plan and refuses the whole export with a 422 that lists every rejected or non-exportable suggestion (already executed, failed, skipped, or still metadata-pending), rather than silently exporting a smaller script; export never mutates session state. Exported scripts cannot guarantee that the filesystem still satisfies its preconditions when the script is later run. They repeat the same safe defaults as the executor: they do not embed destructive operations beyond the plan, they abort on unexpected destination or source state rather than blindly overwriting, a move re-verifies the source's recorded full-content hash when analysis recorded one (a large file carries only the sampling hash, which a script cannot recompute, so the script says in a comment that it checks existence but not content), a duplicate delete confirms that its recorded keeper still exists with the same content before removing anything (so a script cannot delete the last copy), and a symlink repair confirms the link still carries the raw target recorded at analysis before repointing it. A cross-filesystem move is refused at run time with an explicit abort that points at the native executor, because a shell script cannot reproduce the verified copy, hash check, no-replace publish, and source-removal protocol safely; the POSIX export compares device numbers and uses `mv -n`, while the PowerShell export uses `[System.IO.File]::Move`/`[System.IO.Directory]::Move`, which wrap the Win32 no-replace rename and fail on an existing destination or a cross-volume move instead of falling back to an unverified copy. The native executor remains authoritative for validation and safety.

### Race Condition Handling

- Files are re-stat immediately before execution. File identity is the platform object identity: device number plus inode (`st_dev`, `st_ino`) on Unix, and volume serial number plus 64-bit file index from `GetFileInformationByHandle` on Windows, read through a handle opened with `FILE_FLAG_OPEN_REPARSE_POINT` so a link's own identity is checked rather than its target's. A successful Windows file-information query is authoritative even when the volume reports a zero serial; on Unix a zero device or inode means the identity is unavailable. A re-stat that finds a missing, unreadable, or non-regular source, a different object identity, a different size, or (when a full-content hash was recorded) different content marks the suggestion `failed` with the reason in the operation outcome; the reason always says that re-analysis is required. Only mtime drift is tolerated, and only when the content re-checks: a delete requires a full-content hash and re-verifies it, and a move carries the full-content hash analysis computed for it, which it does for every file below the fast-path threshold and for every confirmed group member. A move of a large file above that threshold carries only the sampling hash, which never verifies content but does distinguish a touched timestamp from an edited file: the sample is recomputed and the drift tolerated only when it still matches. A drifted mtime with no recorded hash at all is refused rather than assumed safe. Nothing re-queues or re-analyses the suggestion automatically: a failed suggestion is never executed again, and regenerating it requires starting a new scan, which rebuilds suggestions from the current filesystem state. The rest of the batch continues; one invalid file never blocks unrelated operations. When the platform cannot provide an object identity, every suggestion is refused with `no native object identity on this platform; re-analysis required` rather than executed, so identity-degraded platforms (for example FAT-style filesystems reporting a zero inode) are unsupported by the executor until identity handling is designed for them.
- A file lock is not held during interactive approval (TUI/SPA). A file that changes between review and execution is caught by the re-stat above, and one that changes before execution is caught by re-validation (`POST /validate`, run automatically before execute and export), which marks the suggestion rejected with its `rejection_reason`; the frontends show the status and reason. There is no mid-review push notification or in-place suggestion refresh.

## Output & Reporting

### Scan Summary

Pretty-printed table or JSON/TOML containing:
- Total files scanned in the primary scan
- Total symlinks indexed for repair across the platform's home directory
- Suggestions by type and Asset Kind
- Estimated space reclaimed (for deduplication)

### Machine-Readable Output (`--format json|toml`)

`output.format = "json"` or `"toml"` (or `--format json|toml`) applies to the `--execute` and `--export` outputs only: the plain scan summary is always pretty. In json/toml mode the CLI emits a single structured document to stdout containing the union of the service data types that apply to the mode: the scan root, platform, `ScanSummary`, the full `Suggestion` batch when suggestions are shown, and the `ExecutionReport` when executing with the pieces absent from the mode omitted. Per-operation progress during `--execute` is structured logging and goes to stderr in these modes, so stdout carries exactly one parseable document. The shape is exactly the corresponding "Service API" data types, not a new schema; `summary` matches `ScanSummary` as returned by `GET /report/summary`. TOML output omits optional and null-valued fields (TOML has no null); JSON output follows the API representation. Diagnostics and structured logging continue to go to stderr in every format. "Pretty" is the human-facing default and has no schema of its own.

### Logging

- Structured logging to stderr (level controlled by `-v` / `-q`)
- Optional log file in the platform's standard per-user application-data directory
- Audit log of all executed suggestions appended to the platform's standard per-user application-data directory as `audit.ndjson`, alongside the cache database
- Audit log format: newline-delimited JSON (NDJSON), one entry per executed suggestion, containing timestamp, operation type, absolute source path, absolute destination path (if any), and reason. The record also includes the absolute scan root used for discovery.
- The audit log is append-only, persists across sessions and restarts, and is never session-scoped; it is not rotated or rewritten. Its file name is fixed (`audit.ndjson`), and `GET /audit` reads it directly (see "Service API > Cache, Audit & Reporting").
- Exported scripts do not append to the audit log: they run outside the service and their later execution is not audited.

## Implementation Notes

- Written in Rust
- Async I/O for scanning and metadata extraction (tokio)
- Modular workspace: `model`, `scan`, `analyze`, `suggest`, `execute`, `service`, `clients` crates plus the `homelinter` CLI binary crate, with the macOS-only `homelinter-desktop` Tauri shell in its own workspace
- The `service` crate is the shared backend implemented by the locally running web server; the CLI, the TUI, and the SPA (`webui/`) are clients of it

### Implementation status

The core pipeline and the HTTP service API are implemented and exercised by an end-to-end suite (unit and integration tests across all crates, including service API tests that drive real scans, executions, exports, config PUT, cache clear, and an SSE connection over TCP):

- `model` owns the error envelope, host-native path rules, Asset Kind classification, printf-style format strings, TOML/JSON config deep-merge and validation, suggestion/session types, and SHA-256 hashing.
- `scan` implements primary discovery, the home-wide symlink pass, ToolSet detection for optional external tools, and repository atomicity.
- `analyze` filters out unmanaged files (those that classify to no Asset Kind), then fills provenance and content hashes on the remainder, runs the embedded metadata extractor chain (photos/videos via exiftool then the built-in EXIF reader, audio via exiftool then the built-in `lofty` reader, documents via `pdfinfo` and the built-in container reader), collects repository metadata through the per-VCS adapters (`git`, `hg`, `svn`), extracts filename dates, and deduplicates (keeper = oldest copy). The extractor chain is applied as batched, parallel per-extractor passes, each restricted to the files an earlier pass has not already answered for; content hashing, the fast-path collision confirmation, and repository analysis run on the same worker pool, and the resulting per-file metadata and duplicate groups are identical to the former sequential loop.
- `suggest` generates move and delete suggestions with dependent symlink repairs; delete suggestions always carry the recorded full-content hash required at execution and export time.
- `execute` implements no-replace rename (kernel-atomic `renameat2(RENAME_NOREPLACE)` on Linux, `renamex_np(RENAME_EXCL)` on macOS, and `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING` on Windows, with a hard-link publish for files and a best-effort checked rename where the filesystem offers neither primitive, including directories that cannot be renamed atomically), host-native object identity (Unix `st_dev` + `st_ino`, Windows volume serial + file index), hash-verified delete, dependent symlink repair (Windows uses `CreateSymbolicLinkW` and `GetFileInformationByHandleEx` reparse-tag checks), verified cross-filesystem copy-and-delete with publish-then-delete ordering, and platform script export (POSIX `sh` / PowerShell).
- `service` implements the full REST + SSE API under `/api/v1`, the single-session state machine, batch validation, config merge-and-write, the SQLite cache, and the append-only audit log. Async-accept endpoints (`POST /session/scan`, `POST /execute`) return 202 and deliver their outcomes over SSE.
- `clients` is a small hyper-based HTTP/1.1 + SSE client used by the CLI and the TUI.
- The `homelinter` binary embeds one service instance in-process for the managed CLI flows, the `tui` subcommand, and `web`, per the lifecycle described under "User Interfaces".
- `homelinter-desktop` is the macOS Tauri shell: it links the same service in-process, serves the bundled SPA from the resource directory, waits for health, opens an app-mode WebView window at the loopback origin, and shuts the service down on app exit (see "macOS Desktop Application" and "Distribution & Packaging > macOS").
- `homelinter-app` is the Linux launcher behind the AppImage: the same in-process service with no GUI toolkit, an app-mode browser window against the loopback origin, one reserved browser profile guarded by a single-instance lock, and the same shutdown-on-close invariant (see "Linux AppImage Launcher" and "Distribution & Packaging > Linux").
- `homelinter tui` is the full-screen terminal client (ratatui + crossterm): scanning screen with per-phase stage history, an editable scan-settings form, a two-pane suggestion browser with type/kind/status/metadata/path filters and selection, a manual metadata editor dialog, live execution log, report view, read-only configuration view, a read-only metadata-cache viewer, cache clearing, confirmation and text-input dialogs, and an 80x24 minimum terminal check. Keys: arrows/`j` move, space select, `a`/`A` select all filtered/clear selected filtered, `t`/`k`/`u`/`f`/`c` filters, `/` edit the path filter (persisted to `[ui].path_filter`, see "TUI (Terminal User Interface)"), `x` execute, `m` re-request the highlighted suggestion's provider metadata (confirming first when it clears saved overrides), `M` edit the move's `location`/`subject`/`author`, `b` rebuild the highlighted move suggestion's destination from the effective metadata, `e` export, `n` edit scan settings then scan, `g` open configuration, `v` (or `l`) open the cache viewer from the configuration view, `C` clear the cache, `c` cancel in-flight work and stay in the browser, `?` help, `q`/Esc/Ctrl-C quit (cancelling in-flight work first). In the cache viewer, arrows scroll, `n`/`p` page, `k` cycles the kind filter, and `r` reloads. The TUI mirrors session configuration hashes and surfaces service failure reasons, and it asks for confirmation before executing or exporting a batch whose configuration hash differs from the scan-time hash.

### Documented seams

- **Windows platform primitives**: the native executor is implemented. Identity is the volume serial plus file index; same-filesystem checks compare the volume serial; rename uses `MoveFileExW` without replacement; symlink repair creates a real symbolic link with `SYMBOLIC_LINK_FLAG_ALLOW_UNPRIVILEGED_CREATE` (requiring Developer Mode or `SeCreateSymbolicLinkPrivilege`, reported explicitly when absent) and removes a directory link with `remove_dir`. Only symbolic-link reparse points (`IO_REPARSE_TAG_SYMLINK`) are indexed and repaired; junctions, mount points, and other reparse points are classified separately, never followed, traversed, indexed, or modified, and a move of a tree containing one is refused. Rust's `FileType::is_symlink` alone is not sufficient on Windows because it also matches junctions, so `homelinter_model::identity::link_kind` asks for the exact reparse tag. The exported PowerShell still marks reparse-point repair as a seam (it writes a comment and defers to a native run), because a script cannot reproduce the tag checks safely.
- **Provider plugins**: Built-in transports implement the neutral `custom` completion and reverse-geocode contracts, Ollama chat completions, OpenRouter chat completions, and the Nominatim, Photon, Google, and Mapbox reverse-geocoding APIs. Public geocoders use their native response formats, Nominatim requests include the configured identifying User-Agent contact, and API-key-backed services validate and send credentials only for their configured request. For photos, SVG renders, and video frames with the ollama transport, image bytes are base64-encoded into the chat message's `images` field (bounded by a 20 MiB source cap for photos and SVGs) so vision-capable models analyze the pixels; SVG text is extracted and included alongside the raster. The filename stays in the prompt as a cheap prior, every description and author job is content-keyed (the unit's content identity, not its path) so an edited image, video, or document is re-described while identical content shares one entry, and a cached text-only guess is never served for a vision job (and vice versa), and SVG vision requests use a distinct input marker from other image requests. A video's representative frames are extracted with `ffmpeg` on a provider cache miss as described under "Tooling Strategy"; a vision job that produced no pixels (frame extraction failed) is still applied to the suggestion but not written to the cache, so installing `ffmpeg` later re-describes instead of reusing the text-only result. Photos larger than the effective `max_image_dimension` (default 1024 px on the longest side) have their header probed for dimensions (avoiding a full decode of an already-small image) and are then decoded, downscaled with aspect preserved using the image crate's fast integer downsampler, and re-encoded as JPEG at quality 85 before the request, so the model sees far fewer image tokens - on CPU this turns multi-minute inferences into seconds; undecodable or already-small photos are forwarded unchanged. Every provider request shares one process-wide HTTP client, so keep-alive connections survive across requests instead of a TCP/TLS handshake per image. Every ollama request carries a 30-minute `keep_alive` so the model stays resident between scans, and sizes its context window from the payload (capped by `description.max_context`) so a multi-frame vision request fits instead of being rejected by ollama's 4096-token default, and a scan that plans a vision job spawns a fire-and-forget text-only warmup chat (no timeout) so the model load happens out-of-band instead of eating the worker's provider timeout on the first image request; the per-machine `[limits] provider_timeout_seconds` should cover cold load plus inference (CPU-only vision models can take several minutes). Additional recognition modalities (for example audio transcription) remain future work. The plugin seams (extractor/config schemas, ToolSet detection, cache) are in place. Embedded metadata extraction ships for photos and videos (`exiftool`, then the built-in `kamadak-exif` reader), for audio (`exiftool`, then the built-in `lofty` reader), and for documents (`pdfinfo` for PDFs and a built-in docx/odt/epub reader); the offline provider request loop (job queue, rate-limited worker, cache-first fetch, in-place suggestion refresh with epoch gating and the `metadata_pending` flag) and its format-gated job planner are implemented in the service. Manual metadata overrides are persisted by content identity in the cache database and applied to analyzed files before provider planning, so a user edit suppresses the provider job for that field and wins the value precedence. Document text for description prompts is extracted by the worker per `[document_extraction]` (configured commands, default tools when on the PATH, then the in-process readers - `pdf-extract` for PDF and zip/XML readers for docx/odt/epub), only on a provider cache miss so a scan and a cached description are never blocked on text extraction. A document whose format uses `%a` and has no embedded author is asked of the text description provider under its own cache kind, reusing the same extracted text. When a provider or extractor is unavailable the affected metadata is omitted and analysis continues.
- **TUI and SPA**: both are built. The TUI runs in-process with the service; the SPA is served from `webui/dist` by the `web` command (see "GUI via SPA").

## Developer Environment

- Nix flake (`flake.nix`) with Fenix provides the pinned Rust toolchain via `rust-toolchain.toml` (single source of truth, also usable with `rustup`), rust-analyzer, `pkg-config`, and developer tools (`cargo-nextest`, `cargo-audit`, `cargo-deny`, `taplo`).
- `direnv` entry point is `use flake`; pairing with `nix-direnv` caches the shell for fast reloads.
- The toolchain version is pinned in `rust-toolchain.toml`; the Fenix `sha256` in `flake.nix` is updated when that file changes.
- C dependencies go in `devShells.default.buildInputs`: pkg-config -s dev outputs land in `PKG_CONFIG_PATH` and stdenv rpaths linked libs automatically. `LD_LIBRARY_PATH` is set only on demand (crates that dlopen `.so` files by name, e.g. game engines); see the commented example in `flake.nix`.
- - The SPA (`webui/`) is developed node-free for the Rust workspace: `cargo build` and the test suites never run the JS toolchain, and `webui/node_modules` and `webui/dist` are git-ignored. `webui` locks its dependencies (`package.json` + `pnpm-lock.yaml`) but does not pin the pnpm binary: it declares a `pnpm >= 10` requirement via the `engines.pnpm` field, so any reasonably recent installed pnpm works; run `pnpm install`, `pnpm test` (Vitest), `pnpm build` (Vite), and `pnpm typecheck` there. The dev loop: start `homelinter web --port 8787`, then `pnpm dev` with the Vite proxy (default `HOMELINTER_WEB_PORT` 8787) pointing at the running service.
